### 8. 지급 결과 대조 (webhooks/paypal, tasks/reconcile) 구현 (`feat/paypal-reconcile-webhook` 브랜치)

`/tasks/reconcile`·`/webhooks/paypal` 스텁을 실제 로직으로 교체했다. `src/payouts/reconcile.py`에
결과 대조 핵심 로직을 두고 두 라우트가 공유한다.

- 전 항목 `SUCCESS` → run `SETTLED`, claims `SETTLED`
- `FAILED`/`UNCLAIMED`/`OTHER` 있음 → run `FAILED`, 성공분만 `SETTLED`, 나머지는
  `CONFIRMED`로 되돌리고 `settlement_run_id`를 비움. 예약해둔 `monthly_paid_minor`도 rollback
- `PENDING`이 `PAYOUT_MAX_RECONCILE_ATTEMPTS`를 넘기면 `OTHER`로 간주해 강제 종결 (무한 대기 방지)
- `/webhooks/paypal`은 서명 검증 없이 `payout_batch_id`로 run을 찾아 같은 `reconcile()`을
  앞당겨 호출 — 보조 경로라 실패해도 폴링이 결말을 낸다

이 과정에서 이전 구현에 빠져 있던 gap을 발견해 같이 메꿨다: `/payouts`가
`monthly_paid_minor` 예약 가산(schema-contract.md §7)을 안 하고 있었다 — reconcile의
"실패 시 되돌린다"가 애초에 되돌릴 예약분이 없어 의미가 없었다. `get_sole_recipient_id`
헬퍼로 단일 recipient 전제를 `/payouts`·`/tasks/execute-payout` 양쪽에 동일하게 적용.

TestClient + mock으로 6개 시나리오 검증: SUCCESS 종결, FAILED 종결(claim 롤백 +
monthly_paid_minor 원복), max attempts 초과 강제 종결, webhook known/unknown batch id,
이미 SETTLED인 run 재호출 idempotent no-op.

`feat/paypal-reconcile-webhook` 브랜치 → PR #3 → 즉시 머지(사용자 지시로 리뷰 생략).

## Firestore 연동 (C 트랙 — guards·payouts)

`payouts/fixtures.py`(프로세스 메모리 dict)를 `payouts/store.py`(`google-cloud-firestore`
클라이언트)로 교체. C 소유 4개 컬렉션(`settlement_runs`, `claims`, `recipients`,
`sender_items`) 읽기/쓰기가 실제 Firestore(default) DB로 붙었다.

- 읽기 함수가 반환하는 dict를 in-place mutate하던 기존 패턴은 Firestore에 조용히
  반영 안 되는 write-drop 버그가 되므로, 모든 쓰기 지점을 `update_settlement_run`·
  `update_claim`·`increment_recipient_monthly`·`set_sender_items` 명시적 호출로 교체
  (`guards/routes.py`, `guards/tokens.py`, `payouts/routes.py`, `payouts/reconcile.py`)
- `DRAFT → APPROVED`(승인)와 `APPROVED → EXECUTING`(토큰 소각)는 Firestore 트랜잭션
  안에서 상태를 재확인한 뒤 쓴다 — 동시 요청 이중 승인/이중 소각 방지
- `guards/audit.py`가 `audit_logs`에 실제로 append. 시각 필드는 전부 `datetime`
  객체로 저장(schema-contract.md §1, 문자열 금지)
- `scripts/seed_firestore.py` 추가 — `tests/fixtures/*.json` 8종을 문서 ID로
  덮어써 재실행 가능한 데모 리셋 제공 (fixture 원본은 읽기만, 수정 없음)

**같이 고친 기존 버그**: `payouts/routes.py`에서 `paypal_client.create_payout` import가
`/payouts` 라우트 핸들러 이름과 충돌해 `/tasks/execute-payout`이 실제로는 PayPal이 아니라
자기 자신을 호출하고 있었다. 라우트 핸들러를 `request_payout`으로 개명해 해소
(사용자 확인 후 진행).

실 Firestore 대상으로 검증: approve → payouts(토큰 소각·`monthly_paid_minor` 가산) →
재승인/토큰 재사용 시도(둘 다 409/403) → 별도 프로세스로 out-of-band 재조회해 영속화
확인. fixture 7 두 서브케이스(캡 초과 403, 토큰 없음 403) 응답 문자열 일치 확인.
`execute-payout`·`reconcile`은 PayPal 샌드박스 시크릿이 없어 `paypal_client`를
monkeypatch해 임시 문서로 검증(성공 종결/부분 실패 롤백 모두 기대값과 일치) 후 정리.
검증 후 fixture 시더를 다시 돌려 데모 데이터 원복.

## IAM 격리 검증 + 403 데모 절차 문서화

`terraform plan`으로 IAM/시크릿 관련 드리프트 없음 확인(Cloud Run `scaling` 블록
표현 차이만 존재). `gcloud secrets get-iam-policy`로 4개 시크릿 전부 라이브
IAM 정책 조회해 `payflow-agent` SA가 실제로 어디에도 바인딩 없음을 재확인.

`docs/infra/iam-403-demo.md` 작성 — 심사 시연용 403 데모 절차 2가지:
방법 A(정적 조회, 부작용 없음, 반복 리허설용), 방법 B(임시 `serviceAccountTokenCreator`
부여 → impersonate로 실제 `PERMISSION_DENIED` 캡처 → 즉시 회수, IAM 변경이라 실행은
보류·절차만 문서화). 사전 확인 삼아 grant 없이 impersonate 시도해 `iam.serviceAccounts.
getAccessToken` 거부까지는 재현(=사전 권한도 기본적으로 없음을 재확인). `README.md`
문서 인덱스에 추가.

## IAM 격리 403 실제 캡처 (방법 B 사용자 승인 후 실행)

방법 B를 실제로 실행해 `agent` SA가 PayPal 시크릿에 접근 시도 시 `PERMISSION_DENIED`
받는 장면을 캡처했다. 사용자 확인 후 진행, 3단계(부여 → 캡처 → 회수) 모두 완료.

- 부여 직후 impersonate 시도 시 IAM 바인딩 전파 지연으로 1단계 에러
  (`iam.serviceAccounts.getAccessToken` 거부)가 그대로 재현됨 — 45초 대기 후 재시도
- 재시도 결과: `secretmanager.versions.access` 권한 거부로 진짜 403 캡처
  (`permission: secretmanager.versions.access`, `reason: IAM_PERMISSION_DENIED`)
- `remove-iam-policy-binding`으로 즉시 회수, `get-iam-policy`로 바인딩 빈 것 재확인
- `docs/infra/iam-403-demo.md` 방법 B 절에 실제 에러 문구와 전파 지연 유의사항 추가

## CAS 전이 라이브 검증 + Cloud Tasks enqueue 미구현 버그 발견·수정

`DRAFT → APPROVED`, `APPROVED → EXECUTING` 두 CAS 전이가 실제 동시성 아래서도
정확한지 배포된 API에 대고 직접 검증했다. 그 과정에서 별개의 실제 버그를 발견해
같이 고쳤다 (`fix/cloud-tasks-enqueue` 브랜치, PR #5, 즉시 머지).

**검증**: `run_260817_01SCN01GOLDP`(DRAFT)에 `approve` 5개 동시 요청 → 1개 200,
4개 409(`expected DRAFT`) — Firestore 트랜잭션 CAS 정상 확인. 발급된 토큰으로
`/payouts` 5개 동시 요청 → 5개 전부 409/500, 어느 것도 중복 실행되지 않음(토큰
소각도 CAS로 보호됨) 확인.

**발견한 버그**: `/payouts`가 항상 500을 반환. 원인은 `src/payouts/tasks_queue.py`의
`enqueue_execute_payout`이 `CLOUD_TASKS_QUEUE` 값이 있으면 `NotImplementedError`를
던지도록 미완성 상태였는데, 오늘 오전 Terraform으로 실제 큐가 프로비저닝되면서
그 값이 채워져 미완성 경로가 실행된 것 — `routes.py`는 `QueueNotConfigured`만
잡고 `NotImplementedError`는 안 잡아 그대로 500. 결과적으로 토큰은 이미 소각된
채 run이 `EXECUTING`에 멈춰버림.

**수정**:
- `enqueue_execute_payout`을 `google-cloud-tasks` 클라이언트로 실제 구현 —
  api 자신의 `/tasks/execute-payout`을 OIDC 토큰(`TASKS_SERVICE_ACCOUNT_EMAIL`)
  태스크로 enqueue
- IAM 2건 추가 (`infra/iam.tf`): Cloud Tasks 서비스 에이전트가 api SA의 OIDC
  토큰을 만들 수 있도록 `iam.serviceAccountTokenCreator`, api SA가 자기 자신을
  대상으로 `actAs`할 수 있도록 `iam.serviceAccountUser` (첫 시도는 후자가 빠져
  `PermissionDenied: iam.serviceAccounts.actAs` 500으로 재현·확인 후 추가)
- `infra/cloud_run.tf`에 `TASKS_SERVICE_ACCOUNT_EMAIL` env var 추가
- `Dockerfile`·`pyproject.toml`에 `google-cloud-tasks` 의존성 추가

**재검증**: 두 IAM 권한 모두 반영 후 approve→`/payouts` 재시도 → 200. Cloud
Logging에서 Cloud Tasks가 실제로 `/tasks/execute-payout`을 여러 차례 호출한
것(재시도 포함) 확인 — enqueue 메커니즘 자체는 완전히 동작.

**별개로 발견, 이번 범위 밖**: `/tasks/execute-payout` 내부에서 `PAYPAL_CLIENT_ID`
`KeyError` 500 — Secret Manager에 시크릿 리소스는 있지만 `cloud_run.tf`의 api
컨테이너에 `--set-secrets`로 주입하는 설정이 아직 없음. PayPal Payouts 실제 호출
전에 별도로 처리 필요.

검증 후 `scripts/seed_firestore.py` 재실행으로 데모 데이터 원복.

## XLSX 출력 (세무사 전달용, 계정과목 컬럼 포함) 구현

`GET /settlements/runs/{run_id}/export` 라우트를 `backend/src/settlements/`에

소수 문자열만 기존 `payouts/currency.py`의 `minor_to_paypal_value`로 만들어 절대 규칙
3(금액은 코드가 계산)을 지켰다. 통화별 합계 행 포함. `openpyxl` 의존성을
`pyproject.toml`에 추가하고 `uv sync`로 설치, fixture(`01_golden_path_fx.json`)를
Firestore 클라이언트만 mock해 워크북 생성 결과를 직접 열어 확인.
