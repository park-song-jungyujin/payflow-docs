### 2. Task 5 — `POST /slack/events` (`src/ingest/routes.py`)

앞의 둘을 조립만 한다. 라우트는 분기와 순서만 갖고 로직을 갖지 않는다(`082ade4`).

- 서명 검증 → `url_verification` 챌린지 에코 → bot/비이미지/미등록 사용자 걸러내기 →

- `url_verification`도 **서명 검증을 건너뛰지 않는다.** 이걸 에코하지 않으면 Slack 앱

- 재전송이어도 **enqueue는 다시 한다.** 파싱 태스크는 같은 `receipt_id`를 덮어쓰므로
  멱등이고, 앞 요청이 enqueue 직전에 죽었을 수 있다.
- 큐 실패(`QueueNotConfigured`)는 200으로 ack한다. **3초 ack가 최우선이다** — 여기서

- 반대로 Firestore 트랜잭션 실패는 **문서가 안 남은** 상황이라 200으로 삼키면 영수증이
  조용히 사라진다. 재전송을 받아야 맞아서 명시적 503 + `RECEIPT_INGEST_FAILED` 감사
  로그로 남긴다(계획서에 이 처리를 먼저 추가해두고 구현했다 — `4b28ceb`).

### 4. dedup을 쿼리에서 문서 ID로 — 계획서 명세 결함 (`88d6399`)

**계획서 Task 3의 쿼리 기반 dedup은 동시 재전송에서 뚫린다.** Firestore 트랜잭션은
읽어서 *반환된* 문서에만 락을 건다. `slack_file_id == X` 쿼리가 0건이면 잠글 대상이
없어서, 요청 둘이 각각 "없음"을 보고 서로 다른 `rct_{ulid}`에 쓰면 문서 ID가 달라
**충돌 없이 둘 다 커밋된다.**

유일성은 **문서 ID로 강제해야 한다.** 결정론적 경로에 대한 `transaction.get()`은 문서가
없어도 read set에 들어가 락이 걸린다.

- `receipt_dedup_keys/{slack_file_id}` 컬렉션 신설. `receipts`의 문서 ID 규칙은
  **건드리지 않았다** — `settlements/export.py:36`이 `.document(receipt_id).get()`으로
  읽어서, 바꾸면 이미 배포된 XLSX 출력이 깨진다.
- dedup 문서가 `receipt_id`를 함께 담아 재전송 경로가 쿼리 없이 끝난다.
  `receipts.slack_file_id` 인덱스 의존이 사라져 미검증으로 남아 있던 인덱스 리스크가 없어졌다.
- `ReceiptStoreUnavailable` 신설. 라우트가 `ValueError`를 직접 잡으면 저장과 무관한
  `ValueError`까지 503 + `RECEIPT_INGEST_FAILED`로 뭉뚱그려져 **진짜 버그가 "일시적 저장
  장애"로 위장된다.** `store.py`가 경계에서 도메인 예외로 바꿔 올리고 라우트는 그것만 잡는다.
- `MAX_FILES_PER_EVENT = 5`. 파일마다 트랜잭션 + enqueue를 순차로 돌아 소요가 파일 수에
  선형이다. **초과분은 버리지 않는다** — ack는 즉시 주고 처리 못 한 `file_id`를
  `RECEIPT_INGEST_DEFERRED` 감사 로그에 남긴다. 영수증이 조용히 사라지는 게 3초 초과보다 나쁘다.

한계를 docstring에 명시했다: `FakeTransaction`에는 락·ABORTED·재실행이 없어 **원자성은
검증하지 못한다.** 구조 테스트(`test_dedup_key_is_read_before_any_write`)가 쿼리 기반
회귀는 잡지만, 진짜 동시 재전송 증명은 Firestore 에뮬레이터가 필요해 통합 단계로 미뤘다.

계약 반영(`docs rules/schema-contract.md` §2에 `receipt_dedup_keys` 추가)은 작업 트리
편집까지 했고 커밋·태그는 아직이다.

### 5. 3초 예산 재측정 (enqueue 실모듈 연결 후)

계획서 "구현 후 개정" 3번의 지연 주입 표는 **상한이 들어가기 전** 수치라 다시 쟀다.
코드는 고치지 않았다 — 측정만.

#### 전체 스위트

```
37 passed in 3.88s
```

`--durations=15` 상위:

| 테스트 | 소요 |
|---|---|
| `test_round_trip_stays_within_slack_budget` | 0.77s |
| `test_url_verification_echoes_challenge` | 0.04s |
| 나머지 33건 | 전부 ≤ 0.02s |

예산 테스트를 5회 반복하면 0.77–0.78s로 변동이 거의 없다. 주입한 지연 합이
3 × (0.15 + 0.10) = 0.75s이므로 **라우트 자체 오버헤드는 0.02–0.03s**다.
계획서 Task 5 Step 6의 기대치("0.75s 근처, 나머지 0.1s 미만")와 일치한다.

#### 파일 수 × 지연 재측정

레포 코드를 건드리지 않고 지연만 주입해 TestClient로 왕복을 쟀다(각 3회 평균).
지연 0에서의 라우트 자체 오버헤드는 파일 수와 무관하게 2.4–3.2ms다.

| 파일당 왕복 | n=1 | n=3 | n=5 | n=8 | n=10 |
|---|---|---|---|---|---|
| 50ms×2 | 0.11s | 0.32s | 0.52s | 0.52s | 0.52s |
| 100ms×2 | 0.21s | 0.62s | 1.03s | 1.03s | 1.02s |
| 150ms×2 | 0.31s | 0.91s | 1.53s | 1.53s | 1.53s |
| 200ms×2 | 0.41s | 1.22s | 2.02s | 2.02s | 2.02s |

**n≥5에서 평평해진다.** 상한이 의도대로 동작한다는 뜻이고, 계획서 표에서 3초를
넘겼던 칸(150ms×2 n=10 = 3.03s, 200ms×2 n=8 = 3.23s)이 전부 사라졌다.
최악(파일당 400ms) 실측 2.02s = 3초 예산의 67%, 여유 33%.

#### 이 숫자가 덮지 못하는 것

**enqueue를 실모듈에 연결한 것이 위 측정을 바꾸지 않았다.** 이유:

- `tests/ingest/test_slack_events.py`의 `client` fixture와 예산 테스트가
  `routes.enqueue_parse_receipt`를 통째로 monkeypatch한다. 라우트 경로에서
  `guards/tasks.py`는 한 번도 실행되지 않는다.
- `tests/conftest.py`가 `CLOUD_TASKS_QUEUE`를 `delenv`한다. 스텁을 걷어내도
  실경로는 `QueueNotConfigured`로 **1.6µs**만에 돌아온다 — 네트워크에 닿지 않는다.
- `tests/ingest/test_enqueue.py`는 `tasks_v2.CloudTasksClient`를 페이크로 갈아끼워
  본문 계약(URL·payload·OIDC audience)만 본다. 소요는 재지 않는다.

즉 예산 수치의 enqueue 항은 여전히 **`time.sleep(0.10)` 가정**이다. 실제 비용은
`enqueue_task`가 호출마다 `tasks_v2.CloudTasksClient()`를 새로 만드는 데서 나오는데
(gRPC 채널 + 자격증명 확보), 이건 스위트가 한 번도 재지 않는다. 로컬은 ADC가 없어
대표성 있는 수치가 안 나온다(자격증명 탐색 타임아웃으로 12s 소요 — Cloud Run에서는
메타데이터 서버가 즉답하므로 그대로 옮길 수 없는 값이다).

→ **파일당 enqueue 100ms 가정의 검증은 Cloud Run 배포 후 로그로 미룬다.** 계획서
"이 계획에 넣지 않은 것"의 콜드 스타트 항목과 같은 성격이다. 가정이 2배 틀려도
(파일당 Firestore 200ms + enqueue 200ms = 2.02s) 예산 안이라 상한 5는 유지한다.

### 13. `payflow-frontend` 배포 실패 해소 + Cloud Run drift 정리 (C 작업)

`ci_web.tf`(11번)가 커밋만 되고 `terraform apply`가 안 돌아 WIF provider가 GCP에
없어서 frontend GitHub Actions가 `invalid_target`으로 실패했다.

- `payflow-frontend` WIF provider·`payflow-web-deployer` SA 등 9개 리소스 targeted
  apply로 생성. 워크플로 재실행 후 성공(`check` 32s, `deploy` 2m27s).
- `terraform plan` 중 무관한 drift 발견 — `client`·`client_version`·`build_config`·
  top-level `scaling`이 `gcloud run deploy`가 배포마다 찍는 필드라 매번 diff로
  잡히고 있었다. 세 Cloud Run 서비스(`web`·`api`·`agent`) 전부 `lifecycle
  { ignore_changes = [...] }`에 추가해 고정.
- 남아 있던 진짜 미적용 변경 3건도 apply — `payflow-agent` SA `datastore.user`
  부여, `web`에 빠져 있던 `API_BASE_URL` env(승인 프록시가 쓰는 값), `web`
  `max_instance_count` 20→무제한.
- `template.scaling.min_instance_count=0`은 여전히 apply마다 재등장한다 —
  `gcloud run deploy`가 이 블록을 지우기 때문. 값 자체는 no-op이라 문제 없고,
  데모 촬영 전 `*_min_instances=1`로 올릴 때 정리될 예정(`plan.md`에 이미 메모됨).
