### 6. 영수증 파싱 경로 구현 (Track A) — `src/parsing/`

`RECEIVED`로 남아 있던 영수증을 `PARSED`/`FAILED`로 확정하는 Cloud Tasks 전용 경로. 전날 밤(8/19 23시대) 저장소 경계·PII 마스킹부터 시작해 이날 하루에 나머지를 끝냈다.

- **저장소 경계** (`storage.py`) — `ObjectStore` Protocol + 로컬 구현체. 키는 `images/{receipt_id}.{ext}` · `raw_text/{receipt_id}.txt`로 `receipt_id` 기준이라 재시도가 같은 오브젝트를 덮어써 멱등이다. 이날 밤 GCS 구현체(`payflow-hackathon-2026-receipts`)를 끼웠다.
- **PII 마스킹** (`masking.py`) — Firestore 쓰기 전 단일 창구. 이메일·주민번호·사업자번호·카드·전화 5종. **과대 마스킹이 더 위험하다** — `merchant_name`은 결정론적 매칭의 비교 축이라 상호를 지우면 매칭이 조용히 전부 실패한다. 테스트 절반이 "안 지우는지"를 본다.
- **파싱 출력 모델 + 계정과목 2단계 라우팅** (`models.py`, `categorize.py`) — `ParsedReceipt`에 `amount_minor`가 **없고** `amount_text`만 있다. minor unit 변환은 코드가 `Decimal`로 한다(절대 규칙 3). 인젝션 탐지는 LLM 자기보고가 아니라 원문에 대한 결정론적 패턴 매칭.
- **Slack 원본 다운로드** (`slack_files.py`) — `receipts`에 `url_private`가 없어 `files.info`로 조회 후 봇 토큰으로 GET. 실패를 `TransientParseError`/`PermanentParseError`로 가르는 게 이 모듈의 존재 이유다.
- **파서 경계 + fixture 재생기** (`parser.py`) — 실제 Gemini를 붙이기 전 `tests/fixtures/` 9종을 재생. fixture는 파싱 *결과*라 파서 *입력* 형태로 되돌린다(`category_source != LLM_PARSE`면 계정과목·confidence를 `None`으로).
- **파이프라인** (`pipeline.py`) — 마스킹이 Firestore 쓰기보다 앞. `raw_text`는 반대로 마스킹 없이 객체 저장소에만.
- **`POST /tasks/parse-receipt`** (`routes.py`) — OIDC 필수. HTTP 코드가 큐의 재시도 손잡이다(200 종결 / 503 재시도 / 404 없음).

**파싱이 쓸 수 있는 `receipts.status`는 `PARSED`와 `FAILED` 둘뿐이다.** `NEEDS_REQUERY`는 청구자 에이전트의 판단이라 코드가 대신 쓰면 감사 로그에서 판정 주체를 잃는다(계약 §2). 저confidence·필드 미판독은 상태가 아니라 `UNCLASSIFIED`로 표현된다.

### 7. 리뷰가 잡은 결함 — 기록해 둘 것

태스크마다 리뷰를 붙였고, **8개 중 5개에서 실질 결함이 나왔다. 전부 계획서에 박아둔 코드가 원인이었다.** 계획서에 완성 코드를 넣으면 구현은 빨라지지만 계획서의 버그가 그대로 복제된다.

돈·데이터 경로에 직접 걸린 것들:

- **지수 0 통화에서 소수점 소실** — `"45.000"` + KRW → `45`. **1000배 오차가 예외 없이** 들어가고 `amount_parsed=True`라 게이트도 통과했다. 이제 `None`으로 떨어뜨려 사람이 확인한다.
- **`amount_to_minor`가 `NaN`/`Infinity`에서 예외 전파** — `Decimal()`이 그것들을 정상 파싱해 `except InvalidOperation`이 못 잡았다. 인젝션 영수증에 `Infinity`가 찍히면 태스크가 500으로 죽는다.
- **`slack_file_id` 대괄호 인덱싱** — 계약상 nullable인데(비-Slack 경로) `KeyError`가 어느 예외에도 안 걸려, 그 영수증이 **영원히 `RECEIVED`**로 남았다.
- **enqueue 캐치가 너무 좁음** — `PARSED` 쓴 뒤 예외가 나가면 재시도 때 `SKIPPED`로 빠져 청구자 에이전트 호출이 영구 유실된다.
- **인젝션 미탐 4건** — `previous`만 잡고 `prior`/`above`를 놓쳤다. 같은 계열만 완성하고 회귀 테스트로 박았다.
- **`files.info` 비-JSON 응답**이 어느 분류에도 안 걸리고 누출 / **`ext`가 검증 없이 저장소 키에 삽입**(경로 주입 여지).

### 8. 인수 게이트의 검증 공백 — 변이 테스트로 발견

fixture 종단 회귀를 만든 뒤 리뷰가 **일부러 버그를 심어** 테스트가 잡는지 확인했다. 결과: **1단계 게이트를 2단계 뒤로 옮겨도 174개 전체 스위트가 그대로 통과했다.**

원인은 미묘했다. fixture 재생기가 `DETERMINISTIC_FALLBACK` 영수증의 confidence를 `None`으로 되돌리는데(자기 답 채점 방지, 옳은 동작), 그러면 fixture 02·06에서 1단계와 2단계의 출력이 완전히 같아진다. **§5의 "순서가 핵심"이라는 계약이 원리적으로 관측 불가**였다.

fixture를 고치지 않고(수정 금지) 테스트 파일 안에서 `confidence=0.95`를 얹은 파생 케이스를 만들어 막았다. 재리뷰가 변이 3종을 다시 심어 전부 잡히는 걸 확인했다.
