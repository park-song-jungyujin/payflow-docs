# 2026-08-21

## 작업 개요

오전에 영수증 파싱 경로를 실제 Gemini까지 붙여 **배포·실동작 검증**을 끝냈고(머지 차단 2건 해소, 실제 영수증 1장이 Slack→GCS→Vertex→Firestore 전 경로를 통과), 오후에 **청구 항목(`claims`) 생성**을 구현해 파싱과 정산 사이의 마지막 고리를 이었다. 이로써 영수증 한 장이 송금까지 가는 E2E가 가능해졌다.

## 진행 내역

### 1. Vertex Gemini 단발 호출 파서 구현 (`src/parsing/gemini.py`)

ADK가 아니라 단발 호출이다 — 이미지 1장당 1회, 세션·툴루프 없음(`agent-tools.md`).

- 응답 스키마로 `ParsedReceipt`를 그대로 쓴다. **그 모델에 `amount_minor`가 없는 게 의도다** — 모델은 영수증에 찍힌 문자열(`amount_text`)만 내고 minor unit 곱셈은 코드가 `Decimal`로 한다(절대 규칙 3).
- 프롬프트가 이미지 안의 문구를 `<untrusted_receipt_image>` 블록으로 감싸 **데이터로만** 다루게 한다. "이전 지시를 무시하라"가 적혀 있어도 따르지 않고 `raw_text`에 원문 그대로 옮긴다 — 지우면 인젝션 탐지가 볼 근거가 사라진다.
- 모델 ID는 환경변수. 해커톤 필수 조건이 Gemini 3.5 이상이라 마지막에 버전을 다시 확인해야 하므로 한 곳에서 바꿀 수 있어야 한다.

### 2. 머지 차단 2건 — 배포 영역에서 나왔다

브랜치 전체 리뷰가 잡았다. **개별 태스크 리뷰 10번이 전부 통과했는데도 남아 있었다** — 둘 다 모든 태스크의 파일 범위 밖(배포)이라 구조적으로 볼 수 없었던 것이다.

- **C1 — 컨테이너가 부팅되지 않는다.** `Dockerfile`이 `pyproject.toml`과 **별개로** pip 목록을 하드코딩하는데 `google-cloud-storage`가 빠져 있었다. `src.main` import가 그걸 끌어오므로 머지 즉시 배포되는 리비전이 `ModuleNotFoundError`로 기동 실패한다 — 파싱만이 아니라 payouts·settlements 포함 **API 전체**가 죽는다. 목록에 추가하고, 두 곳을 손으로 동기화해야 한다는 경고 주석을 남겼다.
- **C2 — 컨테이너에서 파서 경로가 조용히 죽는다.** `Dockerfile`이 `src/`만 복사해 이미지에 `tests/fixtures/`가 없다. `FixtureReceiptParser`가 빈 dict가 되고 진짜 영수증에 `KeyError`가 나 분류되지 않은 채 빠져나간다 → 무한 재시도 → 영수증이 `RECEIVED`에 영원히 남는다.

**C2는 fixture를 이미지에 넣는 방식으로 풀지 않았다.** 데모 금액·가맹점명이 진짜 파싱 결과인 척 Firestore에 저장될 수 있고, 그건 `money-safety.md`가 최악으로 정의한 조용한 오류다. 대신 **`_UnavailableParser`**(항상 `TransientParseError` + `PARSER_UNAVAILABLE` 감사 로그)를 도입해 "파서를 쓸 수 없는 상태"를 1급 개념으로 만들었다. 잘못된 데이터를 한 건도 쓰지 않고, 설정을 고치면 큐에 쌓인 태스크가 그대로 재시도된다.

### 3. Vertex 예외를 4xx/5xx로 정확히 분류

`except Exception → TransientParseError`가 너무 넓었다. 잘못된 모델 ID(404), 잘못된 리전, 미지원 mimetype(400, 아이폰 HEIC)이 전부 무한 재시도로 가고 **진짜 파서가 선택됐으므로 `PARSER_UNAVAILABLE` 감사 로그도 안 남았다.**

설치된 `google-genai` 소스를 확인해 `ClientError`/`ServerError`의 `.code`로 분기했다 — 4xx(429 제외)는 `PermanentParseError`, 429·5xx·네트워크는 `TransientParseError`. 어느 쪽이든 예외 원문을 로그에 남긴다.

### 4. 폴백 테스트가 처음부터 no-op이었다

`.env`에 `GEMINI_MODEL_ID`·`VERTEX_LOCATION`을 채우자 스위트가 빨개지며 드러났다.

`_fake_import` 조건이 `name == "src.parsing.gemini" or name.endswith(".gemini")`였는데, `from .gemini import X`는 `__import__('gemini', level=1)`을 부른다 — **조건이 절대 매칭되지 않았다.** 그동안 통과한 건 `VERTEX_LOCATION`이 없어 진짜 생성자가 `KeyError`로 죽어준 우연이었다.

**CI는 `.env`가 없어 계속 초록이었을 것이다** — 로컬만 빨간, 가장 나쁜 형태의 위양성. 명시적 이음매로 바꾸고, 폴백을 무력화해 테스트가 실제로 실패하는지 변이로 확인했다.

### 5. 청구자 에이전트 URL 수정 (PR #10)

`guards/tasks.py`가 태스크 URL을 `OIDC_AUDIENCE + path`로 조립하는데 그건 api 자신의 주소다. 에이전트는 별도 Cloud Run이라 **파싱이 성공할 때마다 api가 자기 자신에게 404를 때렸다.**

`enqueue_task`에 키워드 전용 `audience` 인자를 추가하고 기본값을 `OIDC_AUDIENCE`로 뒀다 — 기존 호출부(payouts 2곳, ingest 1곳)는 한 글자도 안 바뀐다. URL과 OIDC 토큰 audience를 **같은 값으로 함께** 움직인다(하나만 바꾸면 401). `tests/guards/`에 기본 동작 회귀 테스트를 넣어 송금 경로 안전망을 뒀다.

### 6. 라이브 검증 — 모델은 맞았고 리전이 틀렸다

로컬에 `gcloud`가 없어 설치하고 ADC를 잡은 뒤 실제 영수증으로 찔렀다.

첫 시도가 **404 NOT_FOUND** — `gemini-3.7-flash`가 `asia-northeast3`에 없다. **T2 수정이 정확히 이 시나리오에서 값을 했다**: 404가 `PermanentParseError`로 분류되고 예외 원문이 로그에 남았다. 수정 전이었다면 무한 재시도에 감사 로그도 없어 원인 추적이 훨씬 어려웠을 것이다.

모델 × 리전을 탐색한 결과:

| 모델 | asia-northeast3 | us-central1 | global |
|---|---|---|---|
| `gemini-3.7-flash` | 404 | 404 | **OK** |
| `gemini-3.5-flash` | 404 | 404 | **OK** |
| `gemini-2.5-flash` | OK | OK | OK |

`asia-northeast3`에서 되는 건 `gemini-2.5-flash`뿐인데 **해커톤 필수 조건(3.5 이상)에 미달**이라 쓸 수 없다. `VERTEX_LOCATION`을 `global`로 바꿨다. Cloud Run region과는 별개 축이다.

바꾼 뒤 실제 영수증(딤섬관 / 2026-07-27 / 76,500 KRW)으로 종단 확인:

- `merchant_name` = `'딤섬관'` — 사업자번호·전화번호가 안 붙었다
- `transaction_date` = `2026-07-27` — **업로드일이 아니라 결제일** (fake로는 원리상 검증 불가했던 항목)
- `parsed_amount_minor` = `76500` (int)
- `EMPLOYEE_BENEFIT` / `LLM_PARSE` / confidence 0.98

### 7. 배포 반영 후 Slack 실동작 확인

C가 `infra/cloud_run.tf`에 `GEMINI_MODEL_ID`·`VERTEX_LOCATION`을 추가하고 apply했다. 배포된 서비스에 값이 들어간 걸 확인한 뒤 Slack에서 실제로 영수증을 올렸다.

```
01:36:52 RECEIPT_RECEIVED → 01:37:02 RECEIPT_PARSED   (10초)
```

**이번이 Slack 다운로드·GCS 쓰기·Firestore 쓰기가 실제로 돈 첫 실행이다.** GCS에 원본 이미지(1.97MB)와 원문 텍스트가 올라갔고, `raw_text`에는 사업자번호·전화번호가 **마스킹 없이 원문 그대로** 들어 있다(설계대로 — 에이전트의 비신뢰 입력 소스). Firestore의 `merchant_name`은 `'딤섬관'`뿐이다.

`AGENT_SERVICE_URL` 반영 후 재확인 시 `CLAIMANT_ENQUEUE_FAILED`가 사라졌고, Cloud Tasks 응답이 **501**로 바뀌었다 — 태스크가 에이전트 서비스에 도달했고 인증도 통과했다는 뜻이다(URL이 틀렸으면 404, audience가 어긋났으면 401). 청구자 에이전트가 아직 501 스텁이라 `agent_drafts`는 안 생긴다.

### 8. 배포 시점의 안전 실패가 설계대로 작동했다

env 반영 **전**에 올라온 영수증은 `_UnavailableParser`를 타고 `PARSER_UNAVAILABLE` 감사 로그를 5회 남긴 뒤 `RECEIVED`로 남았다. 진단 문구(`fixture corpus empty (cwd=/app...)`)가 원인까지 적어줬다.

잘못된 데이터를 쓰지 않고, 원인을 로그로 남기고, 설정을 고치면 이어진다 — C2 수정이 의도한 그대로다.

### 9. `receipts` 갱신 + `claims` 생성을 단일 Firestore 트랜잭션으로 결합

갈라놓으면 "파싱은 됐는데 청구가 없는" 영수증이 재시도로도 복구되지 않는다 — 재시도 시 `status != RECEIVED`라 `SKIPPED`로 빠지기 때문이다. 오늘 하루에만 같은 형태의 유실이 여러 번 나왔다.

### 10. `is_business`는 `DEFAULT_IS_BUSINESS = True` 상수로 고정

`src/ingest/claims.py`. 청구자 에이전트가 501 스텁이라 코드가 기본값을 넣는다. 반대 방향 오판(업무 경비를 개인용으로 분류)이 더 위험하다 — 청구에서 조용히 빠지고 아무도 모르게 된다. 계정과목으로 추론하지 않는다: `UNCLASSIFIED`는 "계정과목을 못 정했다"이지 "개인 지출이다"가 아니다.

### 11. 생성 즉시 `CONFIRMED`로 진입

청구 단계에 별도 확인을 넣지 않았다. 안전 장치가 집행 직전 승인 한 곳(승인 토큰·금액 해시·CAS·403 게이트·한도 캡)에 몰려 있는 게 설계 의도다.

### 12. `settlement_run_id`를 명시적 `None`으로 씀

Firestore의 `== None` 쿼리가 필드 없는 문서를 못 잡는다. 생략하면 청구가 만들어져도 정산 후보에 **조용히 안 잡힌다** — 에러가 없어 발견이 늦는 형태다. 인수 게이트가 변이 테스트로 이걸 실제로 잡는지 확인했다.

### 13. 계약 갭 발견 — `claims.DRAFT`의 정의 부재

enum에 나열만 돼 있고 의미·전이 규칙이 없다(문서에서 `DRAFT`가 서술된 건 `settlement_runs` 쪽뿐). 제안: **"정산 후보가 아직 아닌 청구"** — 청구자 에이전트 검토 전이거나 `needs_requery` 판정을 받은 것. 계약 반영 여부는 전원 합의 사안으로 남겼다.

### 14. `docs/plan.md` 갱신

- 미결 표의 "업무용/개인용 오판을 어느 단계에서 거를지"에 현재 답을 채웠다 — 집행자 승인 화면이 마지막 방어선.
- Track A 체크박스 "청구 항목 생성 및 `claims` 쓰기" 완료 처리.
