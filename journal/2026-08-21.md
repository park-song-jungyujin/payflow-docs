# 2026-08-21

## 작업 개요

청구 항목(`claims`) 생성 구현 — 파싱이 `PARSED`로 확정한 영수증에서 청구를 만들어 `CONFIRMED`로 넣는다. 이게 끊겨 있던 유일한 고리였고, 이어지면서 영수증 한 장이 송금까지 가는 E2E가 가능해졌다.

## 진행 내역

### 1. `receipts` 갱신 + `claims` 생성을 단일 Firestore 트랜잭션으로 결합

갈라놓으면 "파싱은 됐는데 청구가 없는" 영수증이 재시도로도 복구되지 않는다 — 재시도 시 `status != RECEIVED`라 `SKIPPED`로 빠지기 때문이다.

### 2. `is_business`는 `DEFAULT_IS_BUSINESS = True` 상수로 고정

`src/ingest/claims.py`. 청구자 에이전트가 501 스텁이라 코드가 기본값을 넣는다. 반대 방향 오판(업무 경비를 개인용으로 분류)이 더 위험하다 — 청구에서 조용히 빠지고 아무도 모르게 된다.

### 3. 생성 즉시 `CONFIRMED`로 진입

청구 단계에 별도 확인을 넣지 않았다. 안전 장치가 집행 직전 승인 한 곳에 몰려 있는 게 설계 의도.

### 4. `settlement_run_id`를 명시적 `None`으로 씀

Firestore의 `== None` 쿼리가 필드 없는 문서를 못 잡는다. 생략하면 청구가 정산 후보에 조용히 안 잡힌다.

### 5. 계약 갭 발견 — `claims.DRAFT`의 정의 부재

enum에 나열만 돼 있고 의미·전이 규칙이 없다. 제안: "정산 후보가 아직 아닌 청구"(에이전트 검토 전이거나 재요청 판정을 받은 것). 계약 반영 여부는 전원 합의 사안으로 남겼다 (`plan.md` 미결 참고).

### 6. `docs/plan.md` 갱신

- 미결 표의 "업무용/개인용 오판을 어느 단계에서 거를지" 항목에 현재 답을 채웠다 — 집행자 승인 화면이 마지막 방어선.
- Track A 체크박스 "청구 항목 생성 및 `claims` 쓰기"를 완료 처리.
