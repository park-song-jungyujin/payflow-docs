### 5. 마크다운 200줄 제한 폐지

"모든 마크다운은 200줄을 넘기지 않는다" 규칙을 `CLAUDE.md`에만 적용하도록 좁혔다.

폐지 근거:

- **줄 수가 크기를 반영하지 못한다.** `about_hackathon.md`는 줄 수로 `README.md`의
  4배지만 문자 수로는 1.8배다 (22자/줄 vs 50자/줄). 같은 "200줄 준수" 안에서도
  실제 분량이 2.3배 차이 난다.
- **우회가 쉽다.** README를 218→197줄로 줄일 때 한 편집 중 하나가 구분선 `---` 6개
  삭제였다. 내용은 그대로고 가독성만 나빠졌다.
- **처방이 문제를 키운다.** `원본-1.md`, `원본-2.md`는 주제가 아니라 크기로 자르므로
  이름이 정보를 담지 못하고, 에이전트는 포인터 파일 + 조각 N개를 읽어야 해서
  컨텍스트를 아끼려는 규칙이 컨텍스트를 더 쓴다.
- 규칙 도입 당일 `about_hackathon.md`(799줄)가 이미 위반 상태였다.

`CLAUDE.md`에만 제한을 남긴 이유는 이 파일만 매 세션 자동 로드되어 분량이 곧
반복 비용이기 때문이다. `rules/` 5종이 32~87줄에 안착한 건 제한 때문이 아니라
주제 하나씩 담았기 때문이므로, 규칙도 "크기가 아니라 주제로 나눈다"로 바꿨다.

docs 커밋 후 코드 레포 3개의 submodule 포인터도 함께 올렸다. 포인터가 뒤처지면

### 12. Cloud Tasks → 비공개 Cloud Run OIDC 관통 성공

`payflow-hackathon-2026` 프로젝트에서 `iam.googleapis.com`, `artifactregistry.googleapis.com`,
`cloudbuild.googleapis.com` API 3종 활성화.

`backend/`에 최소 FastAPI 스텁 생성 — `src/main.py`(`GET /`, OIDC 토큰 검증하는
`POST /tasks/ping`), `Dockerfile`, `pyproject.toml`(Python 3.12 핀).

`payflow-api` Cloud Run 서비스를 `asia-northeast3`에 `--no-allow-unauthenticated`로 배포.
`cloud-tasks-invoker` 서비스 계정 생성 후 `roles/run.invoker` 부여. `payflow-queue` Cloud
Tasks 큐 생성. `create-http-task`로 OIDC 태스크를 enqueue해 `/tasks/ping` 호출 → 200 OK
확인(Cloud Run 요청 로그, 앱 로그 양쪽 대조). 첫 태스크는 IAM 바인딩 전파 지연으로 403이
반복되다 약 1분 후 통과했다.

### 13. PayPal 샌드박스 payout 멱등성 확인

`backend/scripts/test_payout_idempotency.py` 작성 — 동일 `sender_batch_id`로 Payouts API를
두 번 호출해 재시도 무해성을 확인하는 1회성 검증 스크립트. `python-dotenv` 의존성 추가,
`.venv`(Python 3.12) 생성.

샌드박스 수취인 `pf_test2@personal.example.com`으로 실행. 1차 호출은 `201`로 배치 생성,
동일 `sender_batch_id`로 보낸 2차 호출은 `400 USER_BUSINESS_ERROR`
(`SENDER_BATCH_ID already exists`)로 거부됨 — 중복 송금 발생하지 않음, 멱등성 확인.

**발견:** PayPal은 동일 `sender_batch_id` 재전송을 "같은 배치로 200 재응답"이 아니라
`400` 에러로 거부한다. `api/src/payouts/` 구현 시 이 에러 형태(`SENDER_BATCH_ID already
exists`)를 진짜 실패가 아니라 "이미 실행됨" 신호로 해석하고, 응답에 포함된 배치 조회
링크로 상태를 확인하는 처리가 필요하다.
### 14. Track A 초안 병합 및 PayPal ID 길이 정정

Track A가 같은 시간대에 별도 초안(`schema.md`)을 작성했고 10번 확정본과 전 영역이
겹쳤다. **정본은 `rules/schema-contract.md` 하나로 두고 초안은 폐기했다.**
스키마 문서가 둘이면 그 자체가 통합 사고의 원인이다. 계정과목 코드값
(`PAYMENT_FEE`/`EMPLOYEE_BENEFIT`), `SettlementFilter` 필드명, 상태값 전면 대문자,
환율 고정 시점 — 초안과 다른 지점은 전부 확정본을 따른다.

**환율은 확정본이 맞다.** 초안은 "승인 시점 고정이면 토큰이 깨진다"고 봤으나, 확정본은
approve에서 환율을 먼저 고정한 **뒤** `approval_amount_hash`를 계산하므로 깨지지 않는다.
초안의 `draft` 생성 시점 고정 제안은 철회한다.

**PayPal ID 길이 — 초안의 "30자 상한"은 근거 없는 수치였다.** 공식 OpenAPI 스펙 기준
`sender_batch_id`는 256자, `sender_item_id`는 **63자**다. 숫자는 틀렸지만 확정본
ID 형식이 상한을 넘는다는 문제 자체는 남는다.

| 값 | 구성 | 길이 | 판정 |
|---|---|---|---|
| `sender_batch_id` | `run_{yyyymmdd}_{ULID26}` | 39 | ✅ ≤ 256 |
| `sender_item_id` | `{run_id}:{recipient_id}` = 39+1+30 | **70** | ❌ > 63 |
| 재발송 `sender_item_id` | `{run_id}:r{n}:{recipient_id}` | **73** | ❌ > 63 |

확정본은 이를 "D2에 실측하고 거부당하면 축약형으로 바꾼다"로 뒀는데, 스펙에 값이
명시돼 있으므로 실측을 기다릴 이유가 없다. **확정본이 이미 적어둔 축약형
`run_{yymmdd}_{ULID 앞 12자}`(23자)를 처음부터 채택**하면 54자 / 57자로 둘 다 들어간다.
D2에 ID 형식을 바꾸면 그 시점엔 이미 `sender_item_id`가 멱등성 키로 쓰이고 있다.

Track A가 확정본에 제안하는 나머지 델타 3건:

| # | 제안 | 이유 |
|---|---|---|
| 1 | `claim_requests.reason` 추가 — `MISSING_CLAIM` / `PARSE_FAILED` / `AMOUNT_MISMATCH` / `UNPAID_NOTICE` | 확정본은 재촉 사유를 구분하지 않는데 `plan.md` Track A는 상황별 문안이 다르고, "10건 중 8건 지급" 통지도 같은 컬렉션을 쓴다 |
| 2 | `receipts.slack_channel_id` · `slack_message_ts` 추가 | 파싱 확인 카드를 업로드한 원 메시지 스레드에 붙이려면 필요하다. 확정본은 `claim_requests.slack_dm_ts`만 갖고 있어 DM 경로만 커버한다 |
| 3 | `plan.md`·`README.md`의 데모 데이터셋을 **8종**으로 갱신 | 확정본이 8종인데 두 문서는 6종이다 |
