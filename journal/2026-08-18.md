# 2026-08-18

## 진행 내역

### 1. Track A 델타 1·2 반영 — 스키마 계약 v0.2.0

8/16 journal 14번에 Track A가 제안해둔 델타 3건 중 1·2번이 미결로 남아 있었다.
재촉 루프와 파싱 확인 카드를 A가 구현하기 전에 계약을 닫아야 해서 반영했다.

#### 왜 필요했나

| 델타 | 없으면 생기는 일 |
|---|---|
| `claim_requests.reason` | 재촉 DM 문안이 상황마다 다른데(파싱 실패 / 금액 불일치 / 미청구), 무엇을 보낼지 고를 근거가 저장되지 않는다. 에이전트가 상황을 추측하게 된다 |
| `receipts.slack_channel_id`·`slack_message_ts` | "파싱했습니다, 이게 맞나요?" 카드를 업로드 원 메시지 스레드에 붙일 수 없다. 확정본이 갖고 있던 `claim_requests.slack_dm_ts`는 DM 경로의 ts라서 다른 대화를 가리킨다. 채널 ID 없이는 `chat.postMessage`도 못 부른다 |

확인해보니 `rules/schema-contract.md` §2와 `backend/src/schemas/models.py` 양쪽 모두
해당 필드가 실제로 없었다.

#### 결정

- `claim_requests.reason` — **필수**, enum 4값. 8/16 원안의 이름을 그대로 쓴다.

  | 값 | 언제 |
  |---|---|
  | `PARSE_FAILED` | 영수증이 흐릿해 파싱 실패 |
  | `AMOUNT_MISMATCH` | 영수증 금액과 청구 금액 불일치 |
  | `MISSING_CLAIM` | 결제 기록은 있는데 청구가 없음 |
  | `UNPAID_NOTICE` | 지급 결과 통지 ("10건 중 8건 지급, 2건 사유") |

- `claim_requests.receipt_id`를 **nullable로 완화**. `MISSING_CLAIM`·`UNPAID_NOTICE`는
  특정 영수증에서 출발하지 않는데 기존 계약은 `receipt_id`를 필수로 못박고 있어
  `reason`만 추가하면 표현 불가능한 조합이 생긴다.
- `receipts.slack_channel_id`·`slack_message_ts`는 **nullable**. Slack 인입이 아닌
  경로(fixture 시딩, 수동 등록)로 만들어진 영수증에는 값이 없다. 비어 있으면 스레드
  답글을 포기하고 DM으로 폴백한다. 한쪽만 채우는 상태는 만들지 않는다.
- `reason`은 분기 근거이지 문안이 아니다. 문안은 청구자 에이전트가 만들고, 에이전트는
  이 값을 **읽기만** 한다. 에이전트가 사유를 지어내는 경로는 두지 않았다.

#### 반영 순서

§13 변경 절차대로 문서 → 코드 → 태그 순으로 했다. 역순 금지.

1. `docs`: `rules/schema-contract.md` §2 — `schema:` 커밋
2. `backend`: `src/schemas/{enums,models,__init__}.py` — `schema:` 커밋 (`affects:` 명시)
3. `backend`: `v0.2.0` 태그

Firestore는 스키마리스라 마이그레이션이 없다. `infra/firestore.tf`는 DB 인스턴스만
관리하고 컬렉션·필드·인덱스 정의를 갖고 있지 않아 인프라 변경도 없다. 실제 영향은
Pydantic 모델과 그걸 import/생성해 쓰는 `agent`·`web`이다.
