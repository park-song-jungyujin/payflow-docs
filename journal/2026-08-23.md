## 다중 수취인 payout 지원 (B)

## 작업 개요

`get_sole_recipient_id`가 막고 있던 다중 수취인 501을 풀었다. `/payouts`,
`/payouts/{run_id}/retry`, `/tasks/execute-payout` 세 곳의 게이트를 제거하고,
recipient별로 base_currency 환산 총액을 계산하는 `payouts/amounts.py`
(`per_recipient_amounts`)를 새로 추가해 단일 PayPal 배치에 recipient당 item을
하나씩 담아 한 번에 보내도록 바꿨다.

## 시작 전 확인한 것

`approve_settlement_run`(`guards/routes.py._lock_fx_and_total`)·`approval_amount_hash`·
`check_caps`(월간 캡)는 이미 다중 recipient를 전제로 짜여 있었고, `paypal_client.create_payout`도
`items: list[dict]`를 받게 설계돼 있었다 — 실제로 단일 recipient로 막힌 곳은
`payouts/routes.py`의 게이트 3곳뿐이었다.

## 결정 사항 (사용자 확인 후 진행)

1. **배치 구성**: recipient별로 별도 배치를 보내지 않고, 단일 PayPal 배치에 recipient당
   item 하나씩 담는다. `sender_batch_id`는 지금처럼 recipient와 무관하게 하나
   (`build_payout_ids`가 이미 그렇게 설계돼 있음), `sender_item_id`만 recipient별로 다르다.
2. **item 매칭**: `get_payout_batch()` 응답의 각 item을 `item["payout_item"]["sender_item_id"]`
   (PayPal 실제 API 응답의 중첩 필드)로 매칭한다. 기존 테스트 mock은 item이 하나뿐이라
   이 필드 없이도 통과했었다 — 이번에 mock도 실제 응답 형태로 맞추고 매칭 로직을
   `sender_item_id` 기준으로 바꿨다(응답 순서에 의존하지 않도록 순서를 일부러 뒤집는
   테스트도 추가).

## 코드 변경

- `payouts/amounts.py` (신규) — `per_recipient_amounts(run)`. run에 걸린 claims를
  recipient_id별로 묶어 `run["fx_rates"]`(승인 시점에 고정된 값, 재조회 안 함)로
  base_currency 환산·합산한다.
- `payouts/routes.py` — `/payouts`·`/payouts/{run_id}/retry`의 monthly_paid_minor
  예약을 recipient별로 각자 몫만 하도록 변경. `/tasks/execute-payout`은 recipient마다
  item을 만들어 단일 배치로 전송, 응답을 `sender_item_id`로 매칭해 recipient별
  `sender_items` 문서를 기록.
- `payouts/store.py` — 이제 안 쓰는 `get_sole_recipient_id` 삭제.
- `payouts/reconcile.py` — 실패 시 monthly_paid_minor 롤백을 `run["total_amount_minor"]`
  (전체 합계) 대신 각 `sender_item["amount_minor"]`(recipient 자기 몫)로 계산하도록
  고쳤다. 이건 버그 수정이기도 하다 — 다중 recipient가 섞인 run에서 한 recipient만
  실패해도 전체 합계만큼 롤백해버리는 문제가 있었다(단일 recipient 전제 때는
  두 값이 같아서 드러나지 않았음).
