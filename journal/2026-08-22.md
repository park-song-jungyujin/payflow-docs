# 2026-08-22

## 작업 개요

Cloud Run `payflow-api`에 `CLAIM_REQUEST_TTL_SECONDS`·`REMINDER_DELAY_SECONDS` env var 적용, terraform state를 로컬에서 GCS backend로 이전.

## 진행 내역

### 1. `payflow-api`에 `CLAIM_REQUEST_TTL_SECONDS`(86400)·`REMINDER_DELAY_SECONDS`(20) env var 추가

`origin/main`의 `infra/cloud_run.tf`·`infra/variables.tf`를 로컬 머신(실 state 보유)에 반영 후 `terraform apply`. plan에 `agent`·`web`의 `max_instance_count: 20 -> null` 드리프트가 섞여 나와 사용자 확인 후 전체 apply. `gcloud run services describe`로 두 env var 값 반영 확인.

### 2. terraform state를 GCS backend로 이전

`payflow-hackathon-2026-tfstate` 버킷(버전관리 on) 신설, `infra/backend.tf` 추가, `terraform init -migrate-state`로 로컬 state를 이전. 이전 전 상태에만 있던 로컬 state 단일 창구 경고 주석(`versions.tf`)을 GCS backend 사실로 갱신. `main`에 직접 push(커밋 `0081b35`).

이전 직후 `agent`·`web`에 `+ min_instance_count = 0` diff가 새로 나타남 — 1번에서 처리한 `max_instance_count` 드리프트와는 별개, 실제 스케일링에 영향 없는 provider 기본값 노출로 판단. apply는 보류.

### 3. `infra/` apply 전용 서비스 계정 `payflow-terraform-admin` 신설

GCS backend 이전으로 state 공유는 해결됐으나, 서버(GCP 리소스)에서 apply까지 하려면 별도 인증 수단이 필요 — 대화형 브라우저 로그인(`gcloud auth application-default login`)은 헤드리스 환경에서 안 됨, 키 JSON 발급은 장기 노출 크리덴셜이라 배제. 대상이 GCP 리소스(VM/Cloud Run)로 확정돼 SA를 리소스에 직접 붙여 ADC로 인증하는 방식 채택. `infra/terraform_admin.tf` 신설 — `roles/editor` + `resourcemanager.projectIamAdmin` + `iam.serviceAccountAdmin` + `iam.workloadIdentityPoolAdmin` + `secretmanager.admin` + `storage.admin` + tfstate 버킷 objectAdmin. `-target`으로 이 8개 리소스만 apply(agent/web의 기존 `min_instance_count` diff는 건드리지 않음). `main`에 직접 push(커밋 `183c156`).

# 재촉 루프 (A)

## 작업 개요

**청구자가 처음으로 무언가를 받게 됐다.** `claim_requests`가 Firestore에
`PENDING`으로 쌓이기만 하던 것을 실제 Slack 메시지로 내보낸다 — 최초 발송 →
무응답 시 1회 재촉 → 만료까지. 곁들여 `feat/claimant-draft-reader` PR을
소유 경계 기준으로 둘로 쪼개 머지를 풀었다.

## PR 분리 — guards 훅을 떼어냈다

### 1. 한 PR이 두 사람의 리뷰를 기다리고 있었다

`feat/claimant-draft-reader`에 `src/guards/agent_drafts.py` 훅(`a7a33a9`)이
섞여 있었다. `src/guards/`는 C 소유라 브랜치 게이트가 걸리는데, PR의 나머지
(청구자 draft 반영 경로)는 전부 `src/ingest/` 소관이라 그 리뷰를 기다릴 이유가
없었다.

**푸시된 커밋을 고치지 않고 새 커밋으로 되돌렸다.** `a7a33a9`의 파일 중
`src/guards/agent_drafts.py`·`tests/guards/test_agent_drafts.py`만 부모 버전으로
돌리고(`1822ec9`), 그 커밋 위에서 다시 원상복구한 브랜치
`feat/claimant-draft-enqueue-hook`을 만들었다(`a86bf88`). 코드는 `a7a33a9`
그대로다.

**openapi 스냅샷은 떼지 않았다.** `a7a33a9`가 훅과 함께 스냅샷도 건드렸지만 그
내용은 `/tasks/apply-claimant-draft` 라우트 항목이고, 라우트 자체는 `88bd997`이
추가한 claimant PR의 것이다. 훅 PR의 스냅샷 변경은 0이다.

머지 순서에 제약이 생겼다 — **claimant 먼저, 훅 나중.** 훅이 enqueue하는
라우트가 claimant PR에 있어서, 순서가 뒤집히면 태스크가 404를 맞는다. 커밋
메시지에 적었다. 둘 다 머지됐다(PR #17 `c58d4b9`, PR #18 `2263e6a`).

### 2. 머지 전에 `main`을 합쳐 스위트를 다시 돌렸다

브랜치가 PR #16(`c770016`)보다 뒤처져 있었다. 머지 자체는 3-way라 B의 수정이
되돌아가지 않지만, 그 브랜치의 437 passed는 B 수정이 **없는** 상태의 숫자였다.
`main`을 머지(`6130ffc`)하고 432 passed 확인 후 푸시했다. 특히
`CLAIM_REQUEST_TTL_SECONDS` 86400 통일은 재촉 루프가 만료 기준으로 그대로 쓰는
값이라, 이 조합에서 확인된 게 의미가 있었다.

## 재촉 루프 — `POST /tasks/remind`

계획서 `plans/2026-08-21-remind-loop.md`대로 6개 태스크. 태스크마다 구현·리뷰를
분리해서 돌렸다.

### 3. 새 라우트를 만들지 않았다

계약 §10에 `POST /tasks/remind`가 **이미 있다.** 최초 발송용 라우트를 따로
만들면 계약을 또 늘려야 한다. 대신 이 라우트가 깨어날 때마다 `claim_request`의
현재 상태를 보고 판정하고, 필요하면 보내고, 다음 깨어남을 **자기 자신을
재예약**해서 만든다 — `payouts/reconcile`이 쓰는 것과 같은 패턴이다.

| 상태 | 조건 | 행동 |
|---|---|---|
| `PENDING` | `slack_dm_ts` 없음 | 최초 발송 → `REMINDER_DELAY_SECONDS` 뒤 자기 재예약 |
| `PENDING` | `slack_dm_ts` 있음, 만료 전 | 1회 재촉 → `REMINDED` → `expires_at`에 재예약 |
| `REMINDED` | `now >= expires_at` | 만료 → `EXPIRED`. 재예약 없음 |
| `RESPONDED` / `EXPIRED` | — | 아무것도 안 함 |

판정(`reminders.decide`)은 **순수 함수**다. Firestore·네트워크·`datetime.now()`
접근이 없고 `now`를 인자로 받는다 — 그래야 경계 시각을 자유롭게 테스트한다.

### 4. 문안은 코드가 짓지 않는다

계약 §9: *"`reason`은 분기 근거이지 문안이 아니다. 문안 자체는 청구자 에이전트가
만든다."* DM 본문은 `agent_drafts/CLAIMANT:{receipt_id}`의
`payload.requery_message`에서만 온다.

**문안이 없거나 비어 있으면 보내지 않는다.** 코드가 대신 문장을 지어내면 절대
규칙의 반대편(문안은 에이전트 몫)을 어긴다. `CLAIM_REQUEST_NO_MESSAGE` 감사
로그만 남기고 `PENDING`으로 둔다 — 에이전트가 다시 돌면 살아난다. 이건 미결에
올렸다: 그 요청은 아무도 못 받는다.

비-dict payload·비-str `requery_message`·공백 문자열을 전부 `None`으로 떨어뜨린다.
폴백 문장은 코드 어디에도 없다.

### 5. 발송 먼저, 표시 나중 — 조용한 유실보다 눈에 보이는 중복

Slack 호출은 Firestore 트랜잭션 안에 넣을 수 없다. "보냈는지" 표시와 실제 발송이
원자적이지 않으므로 둘 중 하나를 골라야 했다.

| 순서 | 실패 시 |
|---|---|
| 표시 먼저 → 발송 | 발송이 실패하면 "보냈다"고 기록된 채 **DM이 영영 안 간다** |
| **발송 먼저 → 표시** | 표시 직전에 죽으면 재시도가 **DM을 두 번 보낸다** |

**발송 먼저를 택했다.** 이 프로젝트는 일관되게 조용한 유실보다 눈에 보이는 중복을
택해왔다. 중복 DM은 청구자가 알아보고 넘어가지만, 안 간 DM은 아무도 모른다.

완화로 발송 직전에 `claim_send_slot`이 트랜잭션 안에서 판정을 재확인한다(정상
재시도는 여기서 막힌다). **이 CAS는 읽기 전용이다** — 예약 표시를 미리 하면 그게
곧 "표시 먼저"가 되기 때문이다. 그래서 동시 워커 둘이 모두 슬롯을 얻는 창은 안
닫힌다. 순서 결정의 대가지 구현 실수가 아니고, 완전히 닫으려면 Slack 발송에
멱등 키가 필요하다.

### 6. 중복 발송 테스트 — "중복이 없다"가 아니라 "중복의 범위"를 고정한다

발송 성공 후 표시 직전에 죽는 시나리오를 실제로 흉내냈다. `record_sent`를
raiser로 바꿔 크래시를 만들고(이때 문서에 흔적이 없는 것도 확인), Cloud Tasks
재전달을 흉내내 라우트를 다시 부른다.

단언하는 것: **두 번째 DM은 실제로 나간다**(이게 이 설계가 감수하기로 한
대가다 — 안 나가면 오히려 설계와 다르다), 그런데 **`claim_requests` 문서는
여전히 한 건이고 id·상태 필드가 오염되지 않는다.**

## 리뷰가 잡은 것

### 7. 만료가 영영 안 일어나는 경로

`expires_at`까지 남은 초를 `int()`로 계산했는데 0 방향 절삭이다. Firestore
타임스탬프에는 마이크로초가 있으므로 다음 깨어남이 거의 항상 만료 시각보다
**최대 1초 이르게** 잡힌다. 그 태스크가 도착하면 아직 `now < expires_at`이라
판정이 `SKIP`으로 떨어지는데, `SKIP` 분기는 재예약하지 않는다 → 그 요청은
`REMINDED`에 영구 정체하고 `EXPIRED`가 되지 않는다. 영수증도 `NEEDS_REQUERY`로
남는다.

**지금 안 터지는 이유가 "Cloud Tasks 전달이 보통 예정보다 늦어서"였다** — 큐
지연에 정확성을 기대고 있었다. `math.ceil`로 고쳤다. 기존 테스트가
`290 <= delay <= 300`이라 299를 통과시켜 못 잡았으므로, `before + delay >=
expires_at`로 "덮는지"를 조이고 1초 미만 잔여 케이스를 추가했다.

### 8. `REMINDER_DELAY_SECONDS` 기본값의 방향이 뒤집혀 있었다

처음 구현은 기본값을 데모 값 20초로 잡았다. 그런데 그 시점에 이 변수가 `.env`·
`infra/` 어디에도 없어서 **배포에서 실제로 도는 값이 20초**였다 — 실제 청구자가
최초 DM 20초 뒤에 재촉을 받는다.

어느 실패가 더 나쁜가로 판단했다. 데모가 하루 걸리는 건 env 하나 넣으면 끝나는
**눈에 보이는 실패**고, 프로덕션이 20초 만에 사람을 재촉하는 건 **눈에 안 보이는
실패**다. 기본값을 86400으로 돌리고 데모가 env로 덮게 했다 — `docs/README.md`가
정한 "환경변수 하나로 데모/실제 전환"과도 맞고, 같은 파일권
`CLAIM_REQUEST_TTL_SECONDS` 기본값(86400)과도 앞뒤가 맞는다.

그 뒤 C가 `infra/cloud_run.tf`에 두 변수를 추가했다(`93d4236`,
`var.reminder_delay_seconds = 20`). 배포는 terraform이 20으로 덮고, env 없는
로컬·테스트는 코드 기본값을 쓴다. 주석의 "이 변수는 아직 어디에도 없다"는
서술을 사실에 맞게 고쳤다(`a4f3bca`).

**그런데 이 정렬 자체가 다음 항목의 결함을 만들었다** — 아래 §12.

### 9. `record_sent`가 스레드 루트 ts를 덮던 것

`SEND_INITIAL` 분기가 상태만 보고 `slack_dm_ts` 존재 여부를 안 봤다. 위 잔여
동시성 창에서 두 워커가 모두 슬롯을 얻으면 두 번째 기록이 루트 ts를 나중 값으로
덮고, 이후 재촉이 엉뚱한 스레드에 달린다. 이미 있으면 쓰지 않고 반환하는 가드로
닫았다 — 중복 DM은 이미 나간 뒤라 부차적이지만 문서 오염은 막는다.

## 발견 — 고치지 않고 드러낸 것 둘

### 10. fixture 05와 코드가 감사 로그 이름에서 어긋나 있다

fixture 05의 `audit_logs`는 `CLAIM_REQUEST_CREATED` / `CLAIM_REQUEST_REMINDED` /
`CLAIM_REQUEST_EXPIRED`인데, 코드가 실제로 내는 건 `CLAIM_REQUEST_SENT`(최초·재촉
공통) + `CLAIM_REQUEST_EXPIRED`뿐이다. **`CREATED`·`REMINDED`는 레포 어디서도
기록되지 않는다.**

처음 쓴 종단 테스트가 fixture JSON 문자열만 읽고 코드 출력과 대조하지 않아서 이
드리프트가 그대로 통과했다. `tests/fixtures/`는 수정 금지 범위라, 테스트를
**드리프트를 명시적으로 고정하는** 형태로 갈아끼웠다 — 루프를 끝까지 돌려 코드가
낸 액션을 `[SENT, SENT, EXPIRED]`로 단언하고 fixture와의 차집합을 못박는다.
어느 쪽에 맞출지는 계약 문제라 미결에 올렸다.

### 11. 재전달 한 번이면 재촉 지연 창이 통째로 무너진다

최초 발송·기록까지 끝난 뒤 Cloud Tasks가 같은 태스크를 재전달하면, 판정이
`PENDING + slack_dm_ts` → `SEND_REMINDER`로 떨어져 **최초 DM 직후에 재촉 DM이
나간다.** `claim_send_slot`은 "이 태스크가 최초 발송용으로 예약된 것"인지 문서에서
구분할 근거가 없어 CAS로도 못 막는다.

재촉이 2회로 늘어나는 건 아니고 타이밍만 무너진다. 고치려면 `claim_request`에
"다음 재촉 예정 시각" 같은 필드가 필요한데 그건 계약 변경이라, 이번 범위에서는
**테스트가 "알려진 결함"으로 고정**만 했다.

## 브랜치 전체 리뷰 — 태스크별 리뷰가 구조적으로 못 보던 것

태스크별 리뷰는 각자 자기 diff만 본다. 브랜치 전체로 보니 두 건이 나왔다.
**8/21에도 같은 일이 있었다** — 개별 태스크 리뷰 10번이 전부 통과했는데 배포
영역의 머지 차단 2건이 남아 있었다.

### 12. 기본 설정에서 재촉이 한 번도 안 나간다

`REMINDER_DELAY_SECONDS` 기본값 86400과 `CLAIM_REQUEST_TTL_SECONDS` 기본값
86400이 **같다.** env가 없으면:

- t0: `apply_claimant_verdict(REQUERY)` → `expires_at = t0+86400`
- t0: 최초 발송 → 재예약 지연 86400 → t0+86400에 깨어남
- t0+86400: 판정이 `SEND_REMINDER`가 아니라 **`EXPIRE`**

→ **재촉 DM 0회.** `CLAIM_REQUEST_EXPIRED` 감사 로그만 정상처럼 남는다. 큐
전달이 이르지 않으므로 경합이 아니라 **결정론적**이다. 이 브랜치의 핵심 기능이
기본 설정에서 조용히 죽는다.

§8에서 기본값을 86400으로 되돌린 판단 자체는 맞았지만(20이면 프로덕션이 20초마다
재촉), **TTL과 같은 값으로 만든 게 문제였다.** 주석에 "TTL 기본값과도 앞뒤가
맞는다"고 적어둔 게 정확히 반대였다 — 둘이 같기 때문에 깨진다.

기본값을 리터럴 대신 `CLAIM_REQUEST_TTL_SECONDS // 2` **관계**로 유도했다. 두
값이 같아서 깨진 문제이므로 관계로 묶어야 재발이 막힌다. env로 TTL만 바꿔도
파생이 따라간다(둘 다 import 시점 모듈 상수).

**e2e 테스트가 이걸 못 잡은 이유가 더 중요하다.** fixture 05의 `expires_at`이
`created + 172800`(TTL의 2배)이라, 테스트가 지연을 86400으로 세팅해도 TTL은
fixture 값을 쓴다 — **코드가 실제로 만드는 TTL 관계를 한 번도 통과시키지
않았다.** fixture를 빌리지 않고 `apply_claimant_verdict`를 실제로 불러
`expires_at = t0 + TTL`을 만든 뒤 env 없는 상태로 루프를 도는 테스트를 추가했다.

### 13. 상태 기계 밖에 흡수 상태가 4개 있었다

`/tasks/remind`는 **자기 재예약이 유일한 생명선**이다(`infra/`에 Cloud
Scheduler·스윕 크론이 없다). 아래는 200으로 끝나면서 재예약을 안 붙여
`claim_request`가 `PENDING`에 영구 고착했다 — **만료조차 안 된다**:

1. **`no_message`** — 계획서 미결은 "에이전트가 다시 돌면 살아난다"고 적었지만
   **그 경로가 없었다.** 에이전트가 draft를 다시 써도 `apply_claimant_verdict`는
   receipt가 이미 `NEEDS_REQUERY`라 `SKIPPED`를 내고 `claim_request_id=None`을
   돌려주므로 재예약이 안 붙는다. 계획서의 완화책이 코드에 없었던 것 —
   태스크 경계를 가로지르는 가정 붕괴다.
2. **`no_target`** — `recipients`에 `slack_user_id`가 없을 때
3. **`SlackSendPermanent`** — `not_in_channel`/`channel_not_found`. **봇이 채널에
   초대돼 있지 않으면 정상 경로 전체가 여기로 빠진다.** 발생 가능성이 가장 높다
4. **`REMIND_ENQUEUE_FAILED`** — 재예약 enqueue 자체가 실패한 경우. 같은 수단으로
   고칠 수 없어 주석만 남겼다

각 경우 영수증은 `NEEDS_REQUERY`, claim은 `DRAFT`로 강등된 채 남아 **정산 후보
선정(`CONFIRMED`만 진입)에서 영구 제외**된다. 정당한 지출이 영영 지급되지 않는데
감사 로그 한 줄 외엔 아무도 모른다 — "조용한 유실보다 눈에 보이는 중복"이라는
이 브랜치 자신의 철학과 정확히 반대다.

1·2·3번에 `expires_at` 만료 태스크를 걸어 흡수 상태를 없앴다. 감사 로그가
죽어도 만료 태스크는 남도록 순서를 잡았다. **DM 폴백(3번의 근본 해결)은 손대지
않았다** — 계획서가 명시적으로 미결로 올린 범위다. 지금 바뀐 건 "조용한 영구
정체"가 "눈에 보이는 종결 상태"가 된 것뿐이고, 사람은 여전히 아무것도 못 받는다.

곁들여 `decide()`의 PENDING 분기에서 만료 검사를 최초 발송보다 앞으로 옮겼다.
판정표에서 바뀐 행은 하나다 — `PENDING` + `slack_dm_ts` 없음 + **이미 만료** →
옛 `SEND_INITIAL`, 새 `EXPIRE`. 옛 동작의 결말은 "DM은 나가고 재예약 지연이
음수가 돼 `PENDING` 영구 고착"이라 새 쪽이 더 방어적이다.

# 청구자 에이전트 입력 (A) — `feat/claimant-snapshot`

## 작업 개요

청구자 에이전트가 영수증 내용을 볼 방법이 없던 문제. `{receipt_id, task_id}`만
받았고, `shared/api_client.py`에는 읽기 기능이 없으며 agent의 Firestore 직접
접근은 `agent_sessions` 하나만 예외다. 안전 확인(settlement_run 스냅샷)·집행자
(candidate_claims)와 같은 방식으로 태스크 본문에 파싱 스냅샷을 싣는다
(커밋 `d9a3b36`). 계약 §10 라우트 변경 없음 — 기존 태스크 본문만 늘었다.

§6 최소화로 7개 필드만 나간다. `recipient_id`·`status`·`slack_*`·`image_gcs_uri`는
판단에 불필요한 식별자라 보내지 않는다. 필드 부재는 키를 빼지 않고 `None`으로
싣는다 — 에이전트가 "없다"와 "안 왔다"를 구분해야 한다.

## 원문을 본문에 싣던 것을 URI로 교체

`d9a3b36`은 7번째 필드로 `raw_text`(원문 자체)를 실었다. **계약과 다르다** —
§9 입력 표는 `raw_text_gcs_uri`다. 세 가지가 걸린다:

1. **마스킹은 해법이 아니다.** money-safety.md의 마스킹 대상은 카드번호·CVC·
   주민등록번호·여권번호 넷뿐이다. 사업자번호·전화번호는 목록에 없어서 마스킹
   함수를 통과시켜도 그대로 남는다. 게다가 마스킹된 원문을 보내면 인젝션 시연
   재료(fixture 06)와 §4c 판단 근거가 같이 죽는다.
2. **Cloud Tasks 본문은 큐에 영속화되고 요청 로그에 남는다.** 신뢰 경계 문제가
   아니라 저장 위치 문제다 — 에이전트가 격리돼 있다는 판단이 이걸 덮지 못한다.
3. **감사 로그 유출 경로.** 원문이 에이전트 컨텍스트에 통째로 들어가면
   `before_tool_callback` 감사 기록이나 draft의 `reason` 필드를 타고
   `audit_logs`로 샐 수 있다 — §2가 "reason에 원문 영수증 텍스트를 흘리지
   않는다"로 명시적으로 금지한 그 경로다. URI로 바꾸면 이것도 같이 닫힌다.

파이프라인은 이미 `updates["raw_text_gcs_uri"]`를 갖고 있어 Firestore 재조회
없이 그대로 넘어간다.

## IAM — `raw_text/` 프리픽스 한정 읽기

agent SA에는 GCS 권한이 **하나도 없었다**(`infra/iam.tf`에 datastore·vertex·
run.invoker만, `infra/storage.tf`는 api SA objectAdmin만). §9이 URI 입력을
전제하므로 읽기 권한이 필요하다 — `infra/storage.tf`에
`agent_receipts_raw_text_read`(`roles/storage.objectViewer`) 추가.

**IAM 조건으로 `raw_text/` 프리픽스에 한정했다.** 버킷 단위로 열면 에이전트가
영수증 이미지 원본까지 읽게 되는데, 이미지↔파싱 결과 검증은 api의 단발 Gemini
호출 몫이지 에이전트 몫이 아니다. 절대 규칙 1(PayPal 자격증명)과는 무관하고,
에이전트 CLAUDE.md의 "Firestore SDK 직접 쓰기 금지"는 Firestore만 명시하므로
충돌이 아니다 — 이 해석을 `storage.tf` 주석에 남겼다.

배포 순서: 이 바인딩 apply → agent 배포. 역순이면 에이전트가 원문을 못 읽는다.

# 청구자 에이전트 실구현 + `/slack/interactions` (A)

## 작업 개요

E2E 사슬의 두 구멍을 메웠다. `/agents/claimant/review`가 501이라 **CLAIMANT draft를
쓰는 쪽이 없었고**(그래서 draft 반영 경로도 재촉 루프도 한 번도 안 돌았다),
`/slack/interactions`가 없어 **`RESPONDED`가 도달 불가능한 상태**였다(모든 요청이
만료됐다). 두 레포에 걸치고 순서는 `api → agent`를 지켰다.

## 청구자 에이전트 (`payflow-agent` `1950cd6`, 브랜치 `feat/claimant-agent`)

**스캐폴딩 툴의 payload를 백엔드가 거부하고 있었다.** `claimant/tools.py`가 보내던
`{classification, requery_message}`는 `parse_claimant_payload`(§9)가 요구하는
`needs_requery: bool`이 없어 `InvalidDraftPayload`가 된다 — LLM만 붙였으면 draft가
전부 `CLAIMANT_DRAFT_APPLY_INVALID_PAYLOAD` 감사 로그만 남기고 조용히 버려졌다.
`tests/test_schema_contract.py`가 enum만 대조하고 payload 내용을 안 봐서 못 잡았다.
계약 4키로 교체하고, 그 테스트에 4키 정확성·bool 타입 단언을 넣었다.

툴 거부 조건 셋: `reason` 공백 / 문안 없는 재요청(재촉 루프가 발송할 게 없어
`PENDING` 고착) / 재요청이 아닌데 문안 있음. 예외가 아니라 `{"status": "error"}`를
돌려준다 — ADK 툴은 반환값으로 LLM에게 말한다.

INSTRUCTION은 **보수적 판정을 이유까지 적어 못박았다.** 잘못 통과시킨 건에는
방어선이 둘 더 있지만(정산 시점 이미지 검증, 집행자 승인 화면) 잘못 거른 건에는
없다. `is_business`는 판단이 안 서면 true — 반대 오판은 청구에서 조용히 빠진다.

`main.py` 배선은 executor 라우트를 본떴고 다른 점은 `entity_id=receipt_id`뿐이다.
원문은 `raw_text_gcs_uri`로 받아 GCS에서 직접 읽는다 — 새 의존성을 넣지 않으려고
JSON API를 `requests`로 부른다(`claimant/receipt_text.py`). **읽기 실패는 500이
아니다**: 구조화 필드만으로도 금액·날짜 부재 판정은 되고, 여기서 죽으면 이 영수증은
draft 없이 남아 재촉 루프가 문안을 영영 못 받는다.

## `/slack/interactions` (`94af397`)

재요청 DM에 버튼을 붙이고(`requery_blocks`, `value=claim_request_id`) 상호작용을
받는다. `claim_request_id`를 버튼에 싣는 이유: 스레드 ts로 역추적하면 쿼리가 필요하고
재촉이 스레드 답글로 나가면 ts가 여러 개가 된다.

본문이 form-encoded(`payload=<json>`)라 서명은 raw body 기준으로 `/slack/events`와
같은 함수를 쓴다. `python-multipart`를 끌어오지 않고 `parse_qs`로 키 하나만 읽는다.

**모양이 예상과 다르면 200 + 감사 로그로 끝낸다** — 400·500을 내면 Slack이 재전송하는데
본문은 같고 사람에게는 매번 오류 배너가 뜬다. 전이는 `mark_responded`의 트랜잭션
CAS로 `PENDING`·`REMINDED`에서만 일어난다: `EXPIRED`를 응답으로 되살리지 않고,
재전송된 같은 클릭에 `CLAIM_REQUEST_RESPONDED`가 쌓이지도 않는다.

## 종단 사슬 현재 상태

Slack 업로드 → `RECEIVED` → 파싱(`PARSED`) → 청구자 에이전트 호출(스냅샷 7필드 +
`raw_text_gcs_uri`) → `submit_receipt_review` → `agent_drafts` → 훅이
`/tasks/apply-claimant-draft` enqueue → `NEEDS_REQUERY` 전이 + `claim_requests`
생성 → 재촉 루프 DM(버튼 포함) → 버튼 클릭 → `/slack/interactions` → `RESPONDED`.

**코드로는 전 구간이 이어졌다.** 끊긴 곳은 없고, 남은 건 실제 GCP·Slack·Vertex에
붙었을 때 각 이음매가 실제로 도는지다.
