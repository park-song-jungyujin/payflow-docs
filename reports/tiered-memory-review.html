3단계(글로벌/팀/세션) 에이전트 메모리 구조 제안 검토

기존 단일 계층 세션 메모리(agent_sessions)를 글로벌·팀·세션 3단계로 확장하자는 제안에 대한 구현 전 검토 — 결론: 구현 보류

검토일 2026-08-22 · Track C(송재훈) · 대상: agent/main.py, agent/shared/memory.py, agent/shared/api_client.py, docs/rules/schema-contract.md §2

복원 안내 이 문서는 2026-08-22 세션에서 작성이 언급되었으나 커밋되지 않아 저장소에서 유실된 상태로 확인됐다(docs/journal/2026-08-22.md §4, docs/SUMMARY.md 2026-08-22행에만 기록 존재). 당시 세션의 원문 자체는 복구할 수 없어, 저널 기록과 현재 코드 (agent/main.py, agent/shared/memory.py)를 대조해 내용을 재구성했다. 세부 문구는 원본과 다를 수 있으나 발견 사항 3가지와 결론(구현 보류)은 저널 원문 그대로다.
2026-08-25 재검증 — §7 최종 계획 추가 §3(untrusted 재주입)·§4(IAM 컬렉션 미제한)는 코드 변경 없이 그대로 재현됨을 확인했다. §5(org_id)는 상황이 바뀌었다 — schema-contract.md는 이제 agent_sessions.org_id를 명시하지만 agent/shared/memory.py· backend enqueue 코드 어디에도 구현되지 않은 문서-코드 드리프트 상태다. 현재 코드베이스 기준 최종 계획을 §7에 추가했다.

Executive Summary

  • 결론 3단계 메모리 구조는 구현하지 않았다 — 검토만 수행. 아래 발견 사항 3가지, 특히 치명적 결함 1건을 해소하기 전에는 계층을 확장할 근거가 없다고 판단했다.
  • 치명적 기존 단일 계층(세션) 메모리에도 이미 결함이 있다 — agent/main.py가 과거 턴을 프롬프트에 재주입할 때 Turn.untrusted 플래그가 저장만 되고 렌더링 시 강제되지 않는다. 계층을 더 늘리기 전에 먼저 고쳐야 할 선행 결함이다.
  • 높음 제안된 글로벌/팀 계층은 agent_sessions 외 새 컬렉션 직접 쓰기를 전제하는데, agent SA의 datastore.user는 컬렉션 단위로 못 좁혀진다. 새 컬렉션마다 "IAM이 아니라 코드로만 지키는 경계"가 하나씩 늘어난다.
  • 중간 검토 시점 기준 Firestore 문서에 org_id 필드가 없어, "팀" 계층을 스코핑할 축 자체가 존재하지 않았다 — 팀 계층은 선행조건 미충족.
  • 같은 날 이어진 멀티테넌시 작업(§5 참고)으로 org_id 선행조건은 이후 해소됐으나, 치명적 결함(§3)과 IAM 경계 문제(§4)는 이 문서 작성 시점 기준 미해결이다.

1. 배경 — 제안 내용

현재 agent_sessions(2026-08-18 도입)은 청구자·집행자 에이전트 각각에 대해 세션 하나(같은 실행 단위의 반복 호출)만 이어붙이는 단일 계층 구조다. 제안은 여기에 두 계층을 추가하는 것이었다:

제안된 3단계 구조
계층범위목적(제안)이 검토에서의 판단
글로벌전체 조직 공통반복적으로 재발하는 패턴(예: 특정 가맹점 분류 규칙)을 세션 경계 없이 공유새 컬렉션 필요 — §4
팀조직(org) 단위같은 조직 내 여러 실행 단위가 학습을 공유스코핑 축 없음 — §5
세션실행 단위 1개기존 agent_sessions 그대로기존 결함 존재 — §3

3. 치명적 결함 — untrusted 태그 미강제

agent/shared/memory.py의 Turn 모델은 턴마다 untrusted: bool을 저장한다. 그런데 agent/main.py가 과거 턴을 프롬프트에 다시 넣을 때는 이 플래그를 쓰지 않는다: 

prior_turns = (
    "\n".join(f"[{t.role}] {t.content}" for t in session.turns)
    if session.turns
    else "(이전 턴 없음 — 이번이 이 영수증의 첫 검토입니다)"
)
...
prompt = (
    f"receipt_id: {receipt_id!r}\n"
    f"task_id: {task_id!r}\n\n"
    f"이전 턴 기록:\n{prior_turns}\n\n"          # ← t.untrusted 무시, 태그 없음
    "<untrusted_receipt_text>\n"
    f"{untrusted_block}\n"                        # ← 이번 턴은 명시적으로 래핑됨
    "</untrusted_receipt_text>\n\n"
    ...
)

이번 호출의 영수증 원문(untrusted_block)은 <untrusted_receipt_text>로 감싸 시스템 지시와 명확히 분리하지만, 과거 턴은 t.content를 그대로 문자열 join한 "이전 턴 기록" 블록에 들어간다. 과거 턴 중 untrusted=True였던 것(즉 이전 영수증 원문)이 있어도 이 블록에서는 신뢰된 시스템 텍스트와 구분되지 않는다.

위험 시나리오 같은 receipt_id에 재시도가 발생해 get_or_create_session이 기존 세션을 이어받는 경우, 1차 시도 때 저장된 영수증 원문(인젝션 문구 포함 가능)이 2차 호출의 "이전 턴 기록"으로 태그 없이 재주입된다. 인젝션 방어가 최초 호출에서만 작동하고 재호출부터는 우회되는 구조다.

agent/shared/memory.py의 append_turn 독스트링은 "content는 <untrusted_*> 같은 래핑을 벗기지 않고 원문 그대로 저장한다"고 명시하지만, 이는 저장 시 래핑을 유지한다는 뜻이지 재주입 시 래핑을 복원한다는 보장이 아니다 — 실제로 main.py 쪽에서 그 복원이 빠져 있다.

4. IAM 경계 확장 문제

agent/shared/memory.py 상단 주석은 이미 이 한계를 인정하고 있다: 

"""schema-contract.md §2 `agent_sessions`, architecture.md "agent" 예외 — ...
`agent` 서비스가 Firestore에 직접 쓰는 유일한 지점이다. 이 모듈이 `agent_sessions`
외 다른 컬렉션을 건드리면 안 된다 — 그 경계는 IAM이 아니라 이 파일 하나로 지킨다
(§2 "IAM 한계")."""

Firestore Admin SDK는 Security Rules를 우회하므로 agent SA에 부여된 roles/datastore.user는 컬렉션 단위 제한이 불가능하다. 현재는 "예외 컬렉션이 agent_sessions 하나뿐"이라는 사실과 shared/memory.py라는 단일 진입점으로 그 경계를 코드 리뷰만으로 지키고 있다. 글로벌·팀 계층을 위해 컬렉션을 1~2개 더 추가하면, 같은 방식(코드 컨벤션)으로 지켜야 할 경계가 그만큼 늘어난다 — 계층마다 "이 컬렉션만 건드린다"를 다시 보증해야 하고, IAM은 여전히 그 보증에 관여하지 않는다.

5. org_id 선행조건 미충족(검토 시점)

검토 시점(2026-08-22 오전, 멀티테넌시 설계 착수 전)의 docs/rules/schema-contract.md는 org_id 필드를 어느 컬렉션에도 정의하지 않은 상태였다. "팀"을 무엇으로 정의할지 (조직? Slack 워크스페이스? 실행자 계정?) 스코핑 축이 스키마에 없어, 팀 계층을 만들어도 무엇을 기준으로 묶을지 결정할 수 없었다.

참고 — 같은 날 해소된 선행조건 이 검토 직후 이어진 멀티테넌시 작업(docs/journal/2026-08-22.md §5·§6)에서 8개 기존 컬렉션에 org_id를 추가하고 orgs·executors 등 4개 컬렉션이 신설됐다. 따라서 "팀" 계층의 스코핑 축 자체는 현재 존재하지만, 이 문서가 다루는 §3·§4의 결함은 그것과 별개로 여전히 미해결이다.

6. 권고(2026-08-22 당시)

  1. §3의 untrusted 재주입 결함을 먼저 고친다. prior_turns 조립 시 t.untrusted가 true인 턴은 <untrusted_receipt_text>와 동일한 방식으로 개별 래핑해야 한다. 계층을 늘리기 전에 기존 단일 계층부터 안전해야 한다.
  2. 글로벌/팀 계층은 새 컬렉션 대신 기존 agent_sessions 확장을 먼저 검토한다. 컬렉션을 늘릴수록 §4의 코드-only 경계가 늘어난다 — entity_id 네임스페이스를 org_id나 글로벌 키로 확장하는 방식이 새 컬렉션보다 IAM 경계 확장을 피할 수 있는지 먼저 검토.
  3. 지금 시점에 3단계 구조를 구현하지 않는다. 해커톤 마감(2026-09-01)까지 남은 시간 대비, 재발 패턴 공유 같은 부가 기능보다 §3 결함 수정과 기존 파이프라인 완결이 우선.

8. 최종 계획 — 현재 코드베이스 기준

새 컬렉션(글로벌/팀 계층)을 만들지 않고 기존 agent_sessions 하나로 세션 계층의 결함을 고치고 org_id 스코핑(사실상 팀 계층 역할)까지 마무리하는 안이다. §4의 IAM 경계를 넓히지 않는 것을 최우선으로 삼았다.

Phase 1 — untrusted 재주입 수정 (필수, 치명적)
파일변경
agent/main.py claimant_review·executor_analyze 두 곳에 중복된 prior_turns 조립 로직을 헬퍼 함수 하나로 통합하고, 턴별 untrusted 플래그에 따라 개별 래핑한다: 
def _render_prior_turns(turns: list[Turn]) -> str:
    if not turns:
        return "(이전 턴 없음)"
    rendered = []
    for t in turns:
        if t.untrusted:
            rendered.append(
                f"[{t.role}] <untrusted_receipt_text>\n{t.content}\n</untrusted_receipt_text>"
            )
        else:
            rendered.append(f"[{t.role}] {t.content}")
    return "\n".join(rendered)
두 라우트의 prior_turns = ... 블록을 이 호출로 교체.
Phase 2 — org_id 스코핑 실제 연결 (문서-코드 드리프트 해소)
파일변경
agent/shared/memory.pyAgentSession에 org_id: str 추가. get_or_create_session에 org_id 파라미터 추가(신규 세션 생성 시에만 반영 — 기존 세션은 조회로 이어받으므로 재기입 불필요). find_prior_session_summary의 필터 체인에 FieldFilter("org_id", "==", org_id) 추가 — 이 한 줄이 §7에서 지적한 조직 간 누출을 막는다.
backend/src/parsing/enqueue.pyenqueue_claimant_review의 payload에 "org_id": receipt.get("org_id") 추가 — 이미 조회돼 있는 receipt dict에서 꺼내기만 하면 됨, 새 조회 불필요.
backend/src/settlements/enqueue.pyenqueue_executor_analyze에 org_id 인자 추가, 호출부(정산 실행 라우트)에서 settlement_run의 org_id를 그대로 전달.
