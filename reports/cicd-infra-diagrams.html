  • CI/CD (전부 배포 성공 확인됨): 레포 3개가 각자 main push 시 자기 자신만 배포한다 — 모노레포 단일 파이프라인이 아니라 완전히 독립된 워크플로 3개. 인증은 서비스 계정 키 없이 Workload Identity Federation(google-github-actions/auth)만 쓴다. WIF pool은 github-actions 하나를 공유하지만, provider와 attribute_condition(레포 이름 일치)으로 레포별로 완전히 격리되어 있어 다른 레포 워크플로가 서로의 배포 권한을 흉내낼 수 없다(backend/infra/ci.tf, ci_agent.tf, ci_web.tf).
  • 부분 구현 표시(주황): backend·agent의 deploy.yml은 checkout 직후 바로 gcloud run deploy로 들어간다 — 테스트·lint 게이트가 없다. frontend만 build → typecheck → lint → test를 통과해야 배포 job이 도는 check job을 갖고 있다.
  • 빌드 방식: Dockerfile을 별도 빌드하는 job이 없다 — gcloud run deploy --source .가 소스를 Cloud Build로 넘겨 이미지를 만들고 바로 배포까지 한다(Artifact Registry는 Cloud Build가 내부적으로 사용).
  • 인프라 코드 위치: 세 서비스의 Cloud Run·IAM·Firestore·Cloud Tasks·GCS·Secret Manager·WIF 정의가 전부 backend/infra/*.tf 한 곳에 있다 — 레포별 IaC가 아니라 backend 레포가 전체 인프라의 단일 진실 소스다.
  • 절대 규칙 1이 그림으로 보이는 지점: payflow-agent로 들어가는 화살표 중 Secret Manager/PayPal로 가는 경로가 없다 — iam.tf에서 secretAccessor 바인딩이 payflow-api SA에만 존재하기 때문이다. agent는 Firestore도 agent_sessions 컬렉션만 쓰도록 되어 있지만, 이건 Firestore Admin SDK가 Security Rules를 우회하는 특성상 IAM이 아니라 코드 컨벤션으로 지키는 경계라 점선으로 표시했다.
  • agent 호출 경로: payflow-agent는 public이 아니다 — run.invoker가 payflow-api SA에만 부여되어 있고, 실제 호출은 payflow-api가 Cloud Tasks에 태스크를 넣으면 Cloud Tasks가 api SA 신원의 OIDC 토큰을 만들어 agent를 부르는 경로 하나뿐이다.
  • 회색(미구현) 경로: payflow-api가 영수증을 Gemini로 구조화 출력하는 경로(backend/src/parsing/)는 아직 빈 모듈이다 — Cloud Run·Vertex AI IAM 권한(roles/aiplatform.user)은 이미 붙어 있지만 그 권한을 쓰는 코드가 없다. 반면 agent 쪽 Vertex AI 호출(ADK 세션)은 세 에이전트 베이스라인이 동작하며 실제로 쓰인다.
  • 사용자 접점: 청구자는 Slack만 거친다(payflow-api의 /slack/events webhook — 서명 검증·ack·dedup까지 구현됨). 집행자는 브라우저로 payflow-web에 진입하고, web은 시크릿을 전혀 갖지 않는 BFF로서 승인 등 일부 요청만 payflow-api로 프록시한다(현재는 승인 라우트 1개뿐, 대시보드 UI는 미구현).
