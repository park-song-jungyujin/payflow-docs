청구자·집행자 세션 메모리 도입

Payflow 세 에이전트 중 반복 상호작용이 있는 두 에이전트에 대화 이어가기 저장소를 추가한다

작성일 2026-08-18 · Track C(송재훈) · 대상 레포: docs, payflow-agent, payflow-backend/infra

Executive Summary

  • 결정 세션 저장소는 agent 서비스가 직접 소유한다. 대상은 청구자·집행자 두 에이전트뿐이고, 안전 확인 에이전트는 1회성 호출이라 제외한다. "대화를 이어가는 상황"은 실시간 채팅이 아니라 같은 실행 단위(청구 요청/정산 실행)의 반복 호출을 이어붙이는 것으로 정의했다.
  • 사실 기존 아키텍처는 "agent는 Firestore에 api 툴을 통해서만 접근"을 명시적으로 금지 규칙으로 두고 있었다. 이번 결정으로 agent_sessions 컬렉션 하나에 한해 명시적 예외를 만들었다.
  • 사실 claimant/·executor/의 실제 에이전트 로직(agent.py)은 아직 구현돼 있지 않다(각각 Track A·B 담당, 현재 라우트는 501 스텁). 이번 작업은 그 에이전트들이 나중에 붙일 메모리 계층까지만 다룬다 — 실제 업무 로직은 범위 밖.
  • Firestore는 스키마리스라 DDL 마이그레이션은 없다. 배포는 IAM 적용 → agent 배포 순서만 지키면 된다.
  • 위험 고지 Firestore Admin SDK는 Security Rules를 우회하므로, agent SA에 부여한 datastore.user는 컬렉션 단위로 좁힐 수 없다. "agent_sessions만 쓴다"는 경계는 IAM이 아니라 코드 컨벤션과 리뷰로만 지켜진다.
  • 세션 요약은 LLM이 아니라 코드가 결정론적으로 생성한다. 압축된 요약이 다음 세션에 "이미 검토된 정보"로 재유입되며 인젝션 검열을 우회하는 경로가 되는 것을 막기 위함이다.

1. 배경 — 왜 요청과 기존 구조가 맞지 않았나

원 요청은 "사용자별 대화 기록이 DB에 저장되고, 세션이 이어질 때는 전체 기록이, 새 세션에서는 이전 세션 요약이 들어가는" claude-mem류 구조였다. 그런데 Payflow의 세 에이전트는 애초에 사람과 실시간으로 채팅하는 구조가 아니다 — api가 파이프라인 단계마다(영수증 인입 직후 / 정산 실행 시 / 승인 카드 렌더 직전) Cloud Tasks로 한 번씩 호출하고, 결과는 agent_drafts에 draft로만 쓴다. ADK 세션도 InMemorySessionService로, "재시작 후 살아남을 필요가 없다"는 게 기존 설계 결정이었다.

주의 — 해커톤 필수조건과의 접점 공식 규정은 "단순 chatbot 구조는 탈락 사유"라고 명시한다. 이번 결정은 사람과의 실시간 채팅 UI를 만드는 게 아니라 기존 파이프라인 호출 사이의 문맥 연속성을 추가하는 것으로 범위를 좁혔다 — 이 구분을 데모/제출물 설명에서도 유지해야 한다.

3. 데이터 흐름

실선은 이번 작업으로 추가된 경로(에이전트 ↔ agent_sessions), 점선은 기존 agent_drafts 경로다. 에이전트 간 직접 호출은 여전히 없다 — 각자 자기 entity_id로만 agent_sessions에 접근한다.

왜 턴 기록이 LLM 툴이 아닌가

현재 세션 히스토리 로드와 턴 기록은 진입점(agent/main.py가 될 코드)이 호출 전후로 직접 수행하는 배관(plumbing)이다. "기록을 남길지 말지"는 LLM이 판단할 문제가 아니라서 툴로 노출하지 않았다 — agent-tools.md의 "툴 하나는 한 가지 일만"과 일치한다. LLM에 노출한 유일한 관련 툴은 fetch_full_session_history 하나뿐이다 — 요약만으로 부족할 때 선택적으로 과거 원문을 당겨오는 용도.

검증

Firestore 없이도 로직을 확인하려고 페이크 클라이언트로 스모크 테스트를 돌렸다: 세션 생성 → Firestore에 반영 → 같은 entity_id로 재조회 시 턴이 이어짐 → 비신뢰 래핑이 그대로 보존됨 → 종료 시 요약에 금액 없이 문서 ID·턴 수만 남음 → actor_ref로 이전 세션 요약 조회 성공 → 전체 히스토리 재조회 성공, 모두 통과.

6. 배포·마이그레이션 절차

Firestore는 스키마리스라 DDL은 없다. 새 컬렉션이라 기존 문서 백필도 필요 없다.

  1. docs: rules/schema-contract.md — schema: 커밋 (본문에 영향 레포 명시)
  2. backend/infra: terraform apply로 agent SA의 datastore.user 바인딩 적용
  3. agent: 배포. 순서를 바꾸면 안 된다 — IAM 적용 전에 배포하면 첫 Firestore 접근에서 PermissionDenied로 즉시 실패한다(조용한 실패는 없다)
  4. Track A·B가 각자 claimant/·executor/의 agent.py를 구현할 때 shared/memory.py를 사용
주의 — 복합 색인 find_prior_session_summary는 agent_type·actor_ref·status 동등 필터 3개에 updated_at 정렬을 더한 쿼리라 Firestore 복합 색인이 필요하다. 이 프로젝트는 Terraform에 색인 리소스를 두지 않는 관례라, 첫 호출 시 FailedPrecondition과 함께 콘솔 링크가 온다 — 그 링크로 만들면 된다. 데모 촬영 전에 한 번 트리거해서 미리 만들어 둘 것(색인 생성에 수 분 소요될 수 있음).

7. 한계와 남은 위험

위험 — IAM이 컬렉션 단위로 못 좁혀짐 Firestore Admin SDK(서버 SDK)는 Security Rules를 우회한다. 즉 agent SA에 부여한 roles/datastore.user는 agent_sessions 뿐 아니라 receipts·settlement_runs 등 다른 모든 컬렉션도 기술적으로 읽고 쓸 수 있게 만든다. "이 컬렉션 하나만 쓴다"는 경계는 agent/shared/memory.py가 유일한 창구라는 코드 컨벤션과 리뷰로만 지켜진다. 절대 규칙 1(agent는 PayPal 자격증명 접근 불가)은 여전히 별도 IAM으로 강제되므로 영향이 없지만, 신뢰 경계 문서의 정확성을 위해 명시해 둔다.
범위 밖 — claimant/executor 실제 로직 미구현 agent/claimant/·agent/executor/는 __init__.py만 있는 빈 상태이고 agent/main.py의 해당 라우트는 501 스텁이다 ("로직은 각 트랙(A/B) 담당"이라고 코드 주석에 명시돼 있음). 이번 작업은 그 두 에이전트가 붙일 메모리 계층만 준비했고, 파싱 결과 검토·자연어→필터 변환 같은 실제 업무 로직은 만들지 않았다 — Track C 담당 범위 밖이다.
