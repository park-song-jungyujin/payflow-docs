  • 매칭·claim 점유 둘 다 done으로 승격 (2026-08-25 밤): settlements 라우터의 후보 매칭(금액±윈도우·날짜±윈도우·가맹점명)은 더는 TEMP가 아니라 의도된 결정론적 로직으로 문서화됐다(src/matching/candidates.py 상단 주석 정리). claim을 정산 실행에 묶는 전이도 조건 없이 덮어쓰는 batch write에서 guards/claims.py:link_claims_to_run_cas — 하나의 Firestore 트랜잭션 안에서 CONFIRMED만 재확인해 IN_RUN으로 전이하고, 다른 배치가 먼저 채간 claim은 조용히 배치에서 빼는 진짜 CAS — 로 교체됐다(backend 커밋 ce3a20f).
  • safety agent 정식 배선 (2026-08-25 밤): 정산 실행 생성 직후 executor 분석과 병렬로 /agents/safety/report가 enqueue되고, 응답 결과(risk_report)가 GET /settlements/runs/{id}의 safety_report 필드로 나간다. 여전히 조언자일 뿐 — safety/tools.py 자체 주석대로 한도 초과·중복 송금·CAS 전이 같은 실제 차단은 이 리포트가 비어 있어도 그대로 동작한다.
  • 청구 반려 자동화 정식 배선 (agent PR #14, origin/main): executor agent가 이상징후 서술을 마치고 submit_settlement_analysis를 부르기 전, 개인용도로 의심되는 물품이 있으면 flag_personal_use_items로 POST /agents/executor/reject-items를 직접 호출해 그 물품만 반려한다(executor/tools.py). 사람이 web 체크박스로 하는 것과 최종 효과(_apply_item_exclusion)는 같고, 승인 전까지 사람이 언제든 되돌릴 수 있다.
  • agent_sessions 예외 (v2 파티션): IAM으로 컬렉션 단위를 못 좁히므로, claimant·executor 두 agent가 세션 컬렉션에 한해 Firestore SDK로 직접 R/W한다(agent/shared/memory.py). v2 마이그레이션 이후 단일 agent_sessions가 아니라 agent_sessions__{org_id} per-org 파티션으로 나뉘어 — org_id 자체가 데이터 격리 경계가 됐다(코드 컨벤션 only → 데이터 경계로 강화). 점선은 여전히 "이 경계가 IAM이 아닌 코드·스키마로 지켜진다"는 뜻.
  • GCS 접근 비대칭: api SA는 storage.objectAdmin(images/, raw_text/ 전체 쓰기)이지만 agent SA는 raw_text/ prefix 조건부 objectViewer만 갖는다(backend/infra/storage.tf:32-42, 2026-08-25 추가) — claimant agent가 원본 이미지가 아니라 OCR 텍스트만 읽도록 IAM으로 강제.

  • 3초 규칙: /slack/events는 서명검증 → Firestore raw 저장 → enqueue까지만 하고 바로 200을 돌려준다. 실제 파싱은 Cloud Tasks 콜백(/tasks/parse-receipt)에서 비동기로 처리된다(docs/rules/architecture.md "비동기" 절).
  • 이중 Gemini 호출 경로: 이 파이프라인의 파싱은 src/parsing/gemini.py의 단발 구조화 출력이고, agent의 claimant 판단은 agent/main.py가 여는 별도의 ADK Runner 세션이다 — 서로 다른 신원(api SA vs agent SA)으로 Vertex AI를 호출한다.
  • 멱등성: task_id(예: CLAIMANT:{receipt_id})가 agent_drafts 문서 ID가 되므로 Cloud Tasks 재시도로 같은 태스크가 중복 실행돼도 draft가 덮어써질 뿐 중복 생성되지 않는다.
  • agent → api 콜백 인증: agent가 /agents/drafts·/agents/audit를 부를 때도 OIDC 토큰(agent SA 신원)을 쓰고, api가 이를 검증한다(guards/oidc.py) — 방향은 항상 agent → api이며 그 반대(api가 agent 결과를 기다리는 동기 호출)는 없다.
  • 세션 메모리 v2 (2026-08-25 머지, PR #10): agent_sessions는 단일 컬렉션이 아니라 agent_sessions__{org_id} per-org 파티션이다(agent/shared/memory.py:25 _collection_name). 청구자 첫 턴엔 같은 recipient_id의 닫힌 세션 요약(find_prior_session_summary)과 유사 사건 검색(find_similar_sessions, case_features 임베딩)을 프롬프트에 얹고, 응답 직전 close_session으로 상태를 CLOSED로 전이·summary·summary_embedding을 영속화한다(임베딩 실패해도 종료는 막지 않는다). 요약·쿼리가 같은 format_case_features 포매터를 거쳐 의미 공간을 일치시켰고, 금액 숫자는 특징 추출 단계에서 배제(money-safety.md 준수).
  • 백엔드 페이로드 갭 해소됨 (2026-08-25): parsing/enqueue.py의 _SNAPSHOT_FIELDS에 org_id·recipient_id가 추가돼, claimant 흐름은 이제 항상 실제 org 파티션으로 들어간다 — agent_sessions__unknown 폴백은 사실상 도달하지 않는다. agent 쪽 main.py는 여전히 body.get("org_id", "") 관용 기본값을 두고 있지만, 이를 org_id 누락 시 400으로 명시 거부하도록 굳히는 커밋들이 agent 레포의 미병합 브랜치 fix/agent-sessions-hardening에 있다(main.py diff: org_id 필수화, close_session 멱등성 가드, append_turn ArrayUnion 전환 등).

  • 승인 CAS 트랜잭션: guards/routes.py의 /settlements/runs/{id}/approve는 Firestore 트랜잭션으로 DRAFT→APPROVED 조건부 전이 + FX 환율 고정 + 토큰 해시 저장을 한 번에 한다 — 중복 클릭으로 토큰이 두 번 발급되는 걸 막는다.
  • claim 점유는 이제 진짜 CAS다 (2026-08-25 밤, done): guards/claims.py:link_claims_to_run_cas가 옛 payouts/store.py.link_claims_to_run(조건 없는 batch write)을 대체했다 — 정산 실행 생성 순서도 CAS 성공 이후로 재배치돼, 링크에 실패한 claim이 죽은 run에 남지 않는다. 전부 실패하면 409.
  • PayPal 멱등성: sender_batch_id가 run_id에서 결정론적으로 파생되고 PayPal-Request-Id 헤더로 재시도 안전성을 확보한다 — Cloud Tasks가 같은 execute-payout 태스크를 재시도해도 중복 송금되지 않는다.
  • reconcile은 스스로 재예약한다: PayPal 배치가 아직 처리 중이면 /tasks/reconcile이 자기 자신을 다시 enqueue한다(Pub/Sub이 아니라 Cloud Tasks schedule_time) — 상태 폴링을 위해 agent나 사람이 깨어있을 필요가 없다.

  • 미등록 team_id 처리: Slack 이벤트가 /auth/slack/callback보다 먼저 도착하면 get_or_create_default_org_id()가 데모용 기본 org를 만든다(auth/store.py) — 프로덕션에서는 명시적 워크스페이스 등록이 전제.
  • 온보딩 DM은 2026-08-25 추가: Slack OAuth 콜백이 users.list로 워크스페이스 멤버를 열거해(봇/앱 계정 필터링, 페이지네이션 처리) 각자에게 PayPal 이메일 등록을 요청하는 DM을 best-effort로 보낸다(docs/journal/2026-08-25.md).
